## 1. 阶段目标、边界与关联需求

本阶段完成 `poker-room-experience-upgrade` 的全部首次实现：先建立房间成员、当前手参与者、准备、动态面值、头像配置、房主操作和观众投影的服务端权威语义，再开放与其一致的 Web 管理、观战、设置、主题和响应式交互。阶段完成后，旧 SQLite 状态可安全恢复，资产与私牌不变量保持成立，且桌面、移动端与公共大屏均通过最终门禁。

- 关联功能需求：`FR-001`–`FR-021`
- 关联验收条件：`AC-001`–`AC-026`
- 关联非功能需求：`NFR-001`–`NFR-011`
- 核心边界：
  - `Room.seats` 继续表示全部买入成员，`PokerState.players` 只表示当前手参与者。
  - 当前手开始后加入的成员保持观众身份，绝不进入当前 `PokerState.players`。
  - waiting 与 complete 都采用“房主 + 至少一名已准备成员”才能由房主显式开手；房主不进入准备集合。
  - 正在进行的手牌读取开手时的面值快照；全局新面值只对下一手生效。
  - 房主、普通观众和 display 均不得接收他人的私牌。
  - 所有成员、资产、准备、开手、踢出、退出和房主转让变更都在现有命令幂等与 SQLite 事务边界内完成。
  - 不修改 `deploy/**`、冻结的其他功能工作流或生成目录；修订 4 允许在用户明确授权后，通过既有忽略配置连接 iStoreOS 的 Docker daemon 执行随机命名、完整清理的隔离 smoke，并为该服务器的 legacy builder 在 `Dockerfile` 声明既有 `linux/amd64` 目标的安全默认值；不切换正式 `home-table`、不挂载固定业务卷，也不把真实发布扩入本功能。
