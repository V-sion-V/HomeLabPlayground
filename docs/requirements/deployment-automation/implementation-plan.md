采用 `expanded` 是因为流程会停止真实服务、原子覆盖唯一数据库备份、切换正式目录并在失败时恢复旧数据库，且必须处理信号中断、遗留锁和半完成切换。这里存在难恢复的数据与运维风险，需要明确文件职责、远端状态转换、恢复顺序和验证证据。工作区中的既存牌局改动不与预期部署文件重叠，实施时仍必须逐任务登记并避免改写这些用户工作。

## 2. 项目现状与全局实现依据

### 2.1 当前组件与约束

- 本地目标环境是 Windows PowerShell 5.1；`git.exe`、系统 OpenSSH `ssh.exe`/`scp.exe` 可用，`pwsh` 不可用。
- Git for Windows 提供 `C:\Program Files\Git\bin\bash.exe` 与 POSIX 工具，可用于本地执行远端脚本语法和模拟测试；它不是目标用户部署命令的运行时依赖。
- 当前本机没有 Docker CLI，且用户明确要求在真实部署前尽量完成本地验证，不尝试 Docker 测试；P-001 不运行 Docker，也不连接服务器。
- [deploy/compose.yml](../../deploy/compose.yml) 以 `home-table` 为唯一服务，构建仓库根目录，健康检查访问 `/healthz`，并把固定命名卷 `home-party-game-platform-data` 挂载到 `/data`。
- 现有人工命令从 `deploy` 目录执行 Compose，因此自动化必须继续从正式发布目录下的 `deploy` 子目录调用 Compose，保持现有项目身份和服务标签，不能因为 incoming/previous 临时目录产生第二套服务。
- 当前镜像名固定为 `home-party-game-platform:0.1.0`；Compose 需要增加带现有默认值的 `PARTY_IMAGE` 插值，使提交 SHA 镜像可以构建和切换，同时保持原人工启动兼容。
- 真实首次接管与纠正后受管更新均已成功；P-003 第一次演练把文档候选 `9405972...` 成功发布后由迟到 watcher 停止，随后已按 Q-012 恢复。配置正式目录当前存在，运行镜像和 `.release-sha` 均为 `9405972dcfbb8bb5bdc4a6970317e60ed3fb1cef`，唯一服务及对外健康检查通过，固定卷与唯一备份有效且无部署临时项；纠正演练必须把该 SHA 作为“已有可识别受管旧版本”。
- `node:24.18.0-bookworm-slim` 已实机确认包含 `/usr/local/include/node` 的完整头文件；Dockerfile 已在 `npm ci` 前设置 `npm_config_nodedir=/usr/local`，P-002 新 SHA 完整构建无 `gyp http GET`。
- 当前数据库是 `/data/platform.sqlite`，SQLite WAL/SHM 与其位于同一卷；现有部署文档已经要求停写后冷备份和保留命名卷。
- 项目已有 Node.js 20+、Vitest、TypeScript、ESLint 和构建脚本，无需为本功能新增第三方依赖。新增部署测试可由 Node/Vitest 编排 PowerShell、Git Bash和临时假命令。

## 3. 全局详细设计

### 3.1 组件与依赖方向

1. **本地 PowerShell 编排器**：`deploy/deploy.ps1` 解析参数与忽略配置，执行本地预检、只读远端 no-op 探测、`git archive`、SHA-256、SCP 上传、远端入口调用、阶段日志和退出码映射。
2. **本地配置**：实际文件 `deploy/deploy.config.psd1` 被 Git 与 Docker 构建上下文忽略；仓库只提供 `deploy/deploy.config.example.psd1`。配置不允许密码字段。
3. **远端 POSIX 状态机**：`deploy/remote-deploy.sh` 只依赖 POSIX shell、常见基本工具、Docker Engine 和 `docker compose`；负责锁、权威 no-op 复核、归档校验/解包、构建、冷备份、目录切换、健康等待、回滚和清理。
4. **Compose 接口**：`deploy/compose.yml` 仅把镜像改为 `${PARTY_IMAGE:-home-party-game-platform:0.1.0}`，保留服务名、构建上下文、端口、健康检查和命名卷。
5. **本地验证夹具**：新增部署定向测试，用临时目录和假命令执行真实 PowerShell 与 POSIX 脚本；假远端状态与调用日志是成功、no-op 和恢复断言的权威证据。
6. **运维文档**：`deploy/README.md` 记录配置、命令、单备份覆盖、自动恢复和人工恢复；根 README 只提供入口和边界。

依赖方向为 `deploy.ps1 -> Git/OpenSSH -> remote-deploy.sh -> Docker Compose/Docker/filesystem`。测试替换外部命令边界但不复制部署决策；生产脚本中的同一状态转换必须在夹具中实际执行。

### 3.2 配置、输入验证与凭据

配置和同名显式参数提供：

- `SshHost`
- `SshUser`
- `SshPort`，默认 `22`
- 可选 `IdentityFile`
- `RemoteReleaseDir`
- `RemoteBackupDir`
- `PartyPort`，默认 `3000`
- `HealthTimeoutSeconds`，采用有界正整数默认值

PowerShell 使用参数数组调用原生命令，不拼接本地 shell 命令；主机、用户、端口、路径和超时在远端调用前验证。远端 POSIX 参数必须通过单引号转义或等价的逐参数安全传递，拒绝控制字符和会改变选项解析的非法值。

配置 schema 不包含密码。未配置私钥时不添加 `BatchMode=yes`，让系统 OpenSSH 在控制台正常请求密码；配置私钥时只传 `-i <path>`。任何模式都不添加 `StrictHostKeyChecking=no`，不使用 `sshpass`，不记录认证输入。日志可显示主机、阶段、提交和非敏感路径，但不显示私钥内容、数据库内容或完整环境。

### 3.3 本地编排与幂等快路径

1. 从仓库根解析配置，验证 Git、SSH、SCP、PowerShell 能力和文件路径。
2. 使用 Git porcelain 状态检查已跟踪和未跟踪变更；非空时在任何 SSH/SCP 调用前失败。
3. 读取完整 `HEAD` SHA，并验证提交可归档。
4. 通过一次短生命周期远端锁执行只读探测：比较正式目录的 `.release-sha`、当前 Compose `home-table` 容器的镜像标签与 `healthy` 状态。远端判定 token 必须在 Windows PowerShell 5.1 到系统 `ssh.exe` 的真实参数封送后仍能精确解析；不使用依赖内嵌双引号保留的 `printf "TOKEN\n"` 形式。
5. 三者与本地 SHA 一致时返回 0，只释放探测锁；不创建源码归档、不调用 SCP、不构建、不备份、不停止或重建容器。
6. 非 no-op 时，以不可预测部署 token 创建本地临时目录，使用 `git archive HEAD` 生成只含提交内容的归档并计算 SHA-256；实际本地配置、`.git`、依赖和未提交文件不会进入归档。
7. SCP 只上传到远端唯一临时名；随后以 SSH 调用远端状态机并传入 SHA、归档哈希、正式目录、备份目录、端口、健康超时和 token。
8. 本地 `finally` 清理本地临时目录；远端返回值原样决定成功/失败，恢复成功也保持非 0。

只读快路径不能替代远端权威复核。两个部署在探测后发生竞态时，只有取得长生命周期部署锁的状态机可以继续；后取得锁者必须再次检查 no-op，并在已由前者发布同一 SHA 时清理自己的临时上传后成功结束。

### 3.4 远端锁、日志与中断恢复

- 锁使用正式目录同级的原子 `mkdir`，元数据记录部署 token、远端 PID、进程启动标识、SHA、开始时间和当前阶段。
- 有效 PID 与启动标识仍匹配时，第二个部署必须拒绝并显示非敏感锁信息。
- 正常退出、普通错误、`INT`、`TERM` 与 SSH 断开触发 trap：切换前只清理临时内容；停服或切换后进入与部署失败相同的恢复路径，最后释放锁。
- 进程被强杀或主机掉电后，下一次部署只在 PID/启动标识确认失效时接管遗留锁。锁内阶段日志是恢复依据：切换前可清理；停服后必须先尝试恢复旧目录、旧镜像与部署前数据库并确认健康，不能直接删除锁继续发布。
- 日志阶段稳定为预检、上传确认、构建、停止、备份、切换、健康、回滚和清理。状态文件只含路径、SHA、镜像引用、阶段和退出结果，不含凭据或数据库内容。

### 3.5 远端构建、冷备份和切换

1. 取得长生命周期锁后重新检查 `.release-sha`、运行镜像与健康；若已匹配则清理本次临时上传并 no-op。
2. 在唯一 token 临时目录校验上传归档 SHA-256，校验通过后解包；失败时旧容器、正式目录和唯一备份不变。
3. 从 incoming 的 `deploy` 子目录使用 `PARTY_IMAGE=home-party-game-platform:<full-sha>` 执行 Compose build。只构建镜像，不创建新服务；已有自动化发布时旧容器继续运行，首次接管时保持维护者已手动停服的现状。构建阶段显式把 `npm_config_nodedir` 指向官方 Node 镜像已内置的 `/usr/local` 头文件，避免原生模块编译为同版本头文件额外访问公网。
4. 构建成功后记录配置发布目录内可识别的旧容器、旧镜像和 Compose 状态；存在时停止 `home-table` 写入，但不执行 `down -v`。首次接管的新配置目录中不存在旧服务时，不探测或修改配置目录之外的旧 Docker。
5. 用挂载固定命名卷和备份目录的临时容器，把 `/data/platform.sqlite` 复制到备份目录内的同文件系统临时名；验证非空和 SQLite 文件头后，以原子 rename 覆盖固定 `platform.sqlite.backup`。上一份备份在新临时文件验证完成前不删除。
6. 备份失败时启动旧服务、等待其健康、保留上一份备份并失败退出；不得交换正式目录。
7. 为旧镜像创建带 token 的临时回滚标签，把正式目录原子移动为 token previous，再把 incoming 移为唯一正式目录。
8. 从新正式目录的 `deploy` 子目录以新 `PARTY_IMAGE` 和配置端口执行 `docker compose up -d --no-build --force-recreate home-table`，复用原 Compose 项目身份和命名卷。
9. 在有界时间内轮询 Docker health，拒绝 `unhealthy`、容器退出或反复重启。健康后写入 `.release-sha`，删除 previous、上传归档、临时回滚标签、锁和临时状态；永久只留下当前正式目录、当前镜像与固定单一备份。

首次自动化接管要求已有 `/data/platform.sqlite` 可形成切换前备份；缺失数据库时遵守“无有效部署前备份不得切换”，保留卷并给出人工初始化说明。已有数据卷但没有旧容器/旧镜像时可以备份并尝试启动新版本；新版本失败时停止新服务、保留卷、备份和诊断，明确报告无旧版本可自动恢复。

### 3.6 自动回滚

切换后任一步失败按以下顺序恢复：

1. 停止失败的新 `home-table`，不删除卷。
2. 移走或删除可安全识别的新正式目录，把 previous 还原为唯一正式目录。
3. 以部署前临时回滚标签恢复旧镜像引用。
4. 使用固定备份覆盖卷内 `platform.sqlite`，删除同目录的 `platform.sqlite-wal` 与 `platform.sqlite-shm`。
5. 从恢复后的正式目录启动旧服务并等待健康。
6. 回滚成功时保留固定备份、删除可安全识别的 incoming/previous/归档/锁/临时标签，并以非 0 报告“新版本失败，旧版本已恢复”。
7. 回滚健康失败时停止进一步自动修改，保留卷、备份、旧镜像引用、阶段日志和恢复所需目录，释放或明确标记可安全接管的锁，并输出逐条人工恢复命令。

恢复命令必须使用记录的实际路径、镜像和端口，但不能包含凭据。任何清理只操作带当前 token 且位于配置正式目录同级的精确路径，不能使用未验证的递归目标、通配删除或卷删除。

### 3.7 兼容性、保留上界与可观察结果

- PowerShell 入口以 Windows PowerShell 5.1 语法实现，不依赖 PowerShell 7 专属 API。
- 远端脚本遵守 POSIX `sh`，不使用 Bash 数组、`[[` 或 iStoreOS 未保证的 systemd 功能。
- Compose 保留原默认镜像、服务名、端口语义、healthcheck 和 `home-party-game-platform-data`；自动化只通过环境变量选择 SHA 镜像。
- 构建与上传不进入停机窗口；停机窗口只包含停止、冷备份、目录交换、启动和健康确认。
- 成功、恢复成功和 no-op 都清理 token 临时数据；回滚失败只保留恢复必需现场，不把它误报成正常空间上界。
- 命令成功输出 SHA、镜像、端口、健康状态和是否 no-op；失败输出阶段、当前服务状态、备份位置、Compose 日志命令和人工恢复步骤。

### 3.8 本地验证与真实服务器交接

P-001 的状态化假远端必须执行生产远端脚本并覆盖：

- 脏工作区或非法配置在零远端调用时失败；
- SSH 密钥与交互密码模式的参数边界、主机密钥校验和日志脱敏；
- 归档仅来自 `HEAD` 且远端哈希失败不解包；
- 正常构建、冷备份、目录交换、健康和清理的顺序；
- 同 SHA 健康时 no-op，断言没有 SCP、构建、停服、备份、覆盖、重建，数据库与备份指纹不变；
- 有效并发锁拒绝、遗留锁安全接管和中断阶段恢复；
- 上传、构建、备份、目录交换、新健康和旧健康故障；
- 新健康失败时恢复旧镜像、部署前数据库并删除 WAL/SHM；
- 首次无旧镜像以及自动回滚失败时保留卷/备份并输出人工步骤；
- 正常和已恢复失败后只有一个正式目录、一个备份、当前镜像且无长期临时项。

### 8.2 技术决策

| ID | 结论 | 原因 | 影响 |
