# 家庭聚会游戏平台：远程部署自动化需求

## 1. 背景与目标

当前每次发布都需要人工上传源码到 iStoreOS、远端构建镜像、停止旧 Docker 容器并启动新容器。该过程重复、容易漏掉备份或健康检查，也缺少一致的失败恢复。

本功能提供一个从 Windows 本地执行的单命令部署流程，在不保存服务器密码、不删除持久数据卷的前提下，自动上传已提交源码、远端构建、冷备份数据库、替换容器并等待健康检查。已有自动化发布可识别时，失败会恢复旧镜像和部署前数据库备份；首次自动化接管没有可识别旧版本时，失败会停止新服务、恢复部署前数据库并进入明确的人工恢复状态。

目标调用者是本项目维护者；目标服务器仍是家庭局域网内支持 Docker Compose 的 x86-64 iStoreOS。

## 2. 范围

### 包含范围

- Windows PowerShell 本地部署入口。
- 本地 Git、SSH/SCP 和配置预检。
- 仅发布干净且已提交的 Git `HEAD`。
- 上传版本化源码归档并在远端校验/解包。
- 已有自动化发布可识别时，新镜像构建期间保持旧容器运行。
- 切换前停止自动化可识别的旧服务并对 SQLite 执行冷备份；首次接管允许由维护者在运行命令前停止旧服务。
- 可配置远端备份目录，永久只保留一个备份文件。
- 新容器替换、Docker healthcheck 等待和部署结果输出。
- 健康失败后自动恢复旧镜像及部署前数据库备份。
- 远端永久只保留一个正式发布目录；部署过程可使用临时目录和临时回滚镜像标签，结束后清理。
- 支持 SSH 密钥，也允许终端交互式密码；不得保存密码。
- 部署锁、错误退出、日志提示和人工恢复指引。
- 从尚不存在的配置发布目录首次接管已有固定数据卷；已由维护者停止的旧 Docker/Compose 与旧目录不由本次自动化识别、停止、删除或自动恢复。

### 不包含范围

- GitHub Actions、Webhook、持续部署或推送即发布。
- Docker Registry、镜像仓库或云构建。
- 多服务器、滚动发布、蓝绿双实例或零停机部署。
- 长期发布历史、多个数据库备份或自动异地备份。
- 自动创建 SSH 用户、密钥或修改服务器防火墙。
- 自动升级 Docker、Docker Compose、iStoreOS 或宿主机软件。
- 首次接管时管理、删除或修改配置发布目录之外的旧 Docker/Compose 目录；该旧目录可由维护者暂时保留为人工回退来源。
- 生产数据库模式的向下兼容推断；失败恢复必须使用部署前数据库备份。
- 未经维护者明确授权的真实服务器连接或修改；本次 P-002 首次部署与同 SHA no-op 已获得明确授权，破坏性实机回滚演练延后。

## 3. 已确认的项目事实与约束

- 现有 [deploy/compose.yml](../../deploy/compose.yml) 从仓库根目录构建 `linux/amd64` 镜像，并使用命名卷 `home-party-game-platform-data` 持久化 `/data`。
- 应用数据库位于 `/data/platform.sqlite`，Docker healthcheck 请求容器内 `/healthz`。
- 现有部署原则要求先构建替换镜像，再停止当前容器；升级和回滚必须保留 `/data` 命名卷。
- 当前本地执行环境为 Windows PowerShell；可调用 Git 和 Windows OpenSSH 的 `ssh`/`scp`。
- 目标服务器必须提供 POSIX shell、Docker Engine 和 `docker compose`。
- 自动化不得删除、重建或匿名替换 `home-party-game-platform-data`。
- 用户可通过 GitHub 取得历史源码，因此远端不需要保留历史发布目录；自动失败恢复仍需要在切换期间保留旧镜像的临时引用。
- 用户要求备份文件永久只保留一份，新备份成功后覆盖旧备份，备份目录必须可配置。
- 用户允许 SSH 交互式密码，因此一次部署可能出现标准 SSH/SCP 密码提示；密码不得进入命令行参数、配置、日志或仓库。
- 首次自动化接管使用新的配置发布目录；维护者已手动停止旧 Docker，要求自动化不再探测、停止或恢复旧 Docker，也不修改旧目录。旧目录暂时由维护者保留，不计入自动化所管理的正式发布目录上界。

## 4. 交付与验证策略

- 本功能采用用户明确选择的 `relaxed`。
- 实现可以先于测试，但全部 `core` 验收和项目硬门禁必须通过。
- 安全、凭据、数据完整性、备份、构建、健康检查、兼容性和已声明恢复行为始终阻塞，不因 relaxed 降级。已有旧版本的一体自动回滚由本地确定性故障证据阻塞；首次接管的实机回滚演练按用户要求作为后续独立阶段保留。
- 只有独立证明不影响交付行为的 supplemental 异常才可记录为带严重程度的 `FND-*`，不得把未证明的部署安全问题作为报告项放行。
- 本轮只完成需求澄清；后续规划和实现不得自动连接或操作用户服务器。若最终需要真实部署验证，必须停止并把明确步骤交给用户，或等待用户另行授权。

## 5. 功能需求

### FR-001 单命令入口

项目必须提供一个从仓库根目录调用的 PowerShell 部署入口。成功时返回退出码 0；任何未恢复错误必须返回非 0。

### FR-002 本地部署配置

部署入口必须从 Git 忽略的本地配置或显式参数读取以下值：

- SSH 主机；
- SSH 用户；
- SSH 端口，默认 22；
- 可选 SSH 私钥路径；缺失或认证失败时允许 OpenSSH 交互式密码；
- 远端唯一正式发布目录；
- 远端数据库备份目录；
- 对外服务端口，默认沿用现有 `PARTY_PORT` 语义。

仓库可提供不含真实地址和凭据的示例配置。密码不得成为配置字段。

### FR-003 本地预检与发布来源

部署前必须验证 Git、SSH、SCP 和所需本地能力可用。工作区必须干净，待发布提交必须是当前 `HEAD`；存在已跟踪或未跟踪修改时必须在任何远端变更前拒绝部署。

发布源码必须仅来自当前 Git `HEAD`，发布标识必须包含完整或可无歧义追踪的提交 SHA。不得上传 `.git`、本地配置、依赖目录、构建产物、测试结果或其他未提交文件。

### FR-004 远端预检与并发锁

远端变更前必须验证目标路径可写、Docker 可用、`docker compose` 可用、现有命名卷和自动化所管理的服务状态可识别。首次接管时，配置发布目录不存在且其中没有可识别旧服务是合法状态；自动化不得据此探测或修改配置目录之外的旧 Compose 目录。

部署必须取得远端互斥锁；锁已由其他有效部署持有时必须拒绝并说明。异常退出后不得留下无法判断或永久阻止发布的无主锁，清理规则必须可诊断。

取得锁后必须比较本地 Git `HEAD`、远端当前发布标记、运行容器镜像和健康状态。四者一致且当前服务为 `healthy` 时，部署必须作为幂等 no-op 成功结束：不得重复上传、构建、停止、备份、覆盖发布目录或重建容器。相同提交但服务不健康或发布标记不一致时不得 no-op，必须进入正常部署或恢复流程。

### FR-005 上传与远端构建

源码归档必须先上传到远端临时位置，并在解包前完成完整性校验。解包和构建必须在临时工作目录中进行。

新镜像必须使用提交 SHA 派生的唯一标签。已有自动化发布可识别时，远端镜像构建期间旧容器必须继续运行；首次接管时允许维护者已在命令前停止旧服务。构建失败时不得修改唯一数据库备份或替换正式发布目录，也不得操作配置目录之外的旧 Docker/Compose。

### FR-006 单文件冷备份

新镜像构建成功后，部署必须确保自动化所管理的当前服务已停止写入，再从命名卷冷备份 `/data/platform.sqlite`。首次接管且旧服务已由维护者停止时，脚本可直接进入冷备份，不负责重新识别或停止旧服务。

备份目录必须来自配置。备份必须先写入临时文件并验证成功，再原子替换固定的唯一备份文件；不得先删除上一份备份。成功部署、失败回滚和后续部署都不得在该目录永久累积第二份备份。

停止服务后若备份失败，必须重新启动原服务并以非 0 退出，不得切换镜像。

### FR-007 安全切换

已有自动化发布可识别时，切换前必须为当前运行镜像建立临时回滚标签或等价可恢复引用，并记录当前 Compose 运行参数。首次接管没有可识别旧镜像时，必须明确进入“无旧版本可自动恢复”分支。

部署必须把远端唯一正式发布目录替换为新提交内容，并使用新镜像重建服务。必须复用原命名卷、端口和允许的环境配置，不得执行 `docker compose down -v` 或任何删除数据卷的操作。

### FR-008 健康检查与成功清理

新服务启动后必须在可配置但有界的超时时间内等待 Docker healthcheck 进入 `healthy`，并确认服务未反复重启。

成功后必须：

- 输出提交 SHA、镜像标签、服务端口和健康结果；
- 清理上传归档、临时构建目录、锁和临时回滚镜像标签；
- 确保远端只保留一个正式发布目录和一个数据库备份文件；
- 不删除当前镜像、命名卷或唯一备份。

### FR-009 自动失败回滚

已有自动化发布可识别，且新容器未启动、进入 unhealthy、超时或切换阶段发生错误时，自动化必须：

1. 停止失败的新服务；
2. 使用切换前保存的旧镜像引用恢复旧应用；
3. 从唯一部署前备份恢复 `platform.sqlite`，并清理与该数据库不一致的 SQLite WAL/SHM 文件；
4. 重新启动旧服务并等待其 healthcheck；
5. 保留唯一备份文件和必要失败日志，清理临时目录与部署锁。

回滚成功后部署命令仍必须返回非 0，并明确说明新版本失败、旧版本已恢复。回滚失败时必须返回非 0、停止继续变更、保留可诊断现场，并输出人工恢复步骤。

首次接管没有可识别旧版本时，新服务失败必须停止新服务、从唯一部署前备份恢复数据库、保留卷和诊断现场并返回非 0；不得尝试启动或修改配置目录之外的旧 Docker。旧目录的人工回退由维护者另行决定。

### FR-010 发布目录与保留策略

自动化管理范围内永久只允许一个由配置指定的正式发布目录。部署期间允许使用一个或多个明确标识的临时目录，但成功或已恢复的失败流程结束后必须清理。首次接管前的旧目录属于维护者保留的外部人工回退资产，不由本脚本修改、清理或计入该上界。

远端不永久保存历史源码发布目录。历史源码由 GitHub/Git 提供；后续人工回滚可检出目标提交后再次运行同一部署入口。

### FR-011 SSH 认证与凭据保护

部署必须使用系统 OpenSSH。配置私钥时可免交互认证；未配置私钥时必须允许 OpenSSH 在终端请求密码。

自动化不得读取、缓存、回显或写入 SSH 密码，不得引入明文密码文件、`sshpass` 或把密码放入进程参数。SSH 主机密钥校验不得被全局禁用。

### FR-012 诊断与退出行为

每个主要阶段必须输出简洁状态：预检、上传、构建、停止、备份、切换、健康检查、回滚和清理。

失败输出必须指出失败阶段、远端服务状态、建议查看的 Compose 日志命令、备份位置和下一步。普通输出不得包含密码、私钥、数据库内容或其他敏感信息。

### FR-013 文档与人工边界

部署文档必须说明：

- 首次创建本地配置的方法；
- SSH 密钥和交互式密码两种使用方式；
- 一键部署命令；
- 配置项和默认值；
- 唯一备份文件的位置和覆盖语义；
- 自动回滚行为；
- 从 GitHub/Git 历史提交重新部署的方法；
- 自动回滚失败时的人工恢复步骤。

实现和本地验证不得假装完成真实服务器发布。没有用户另行授权时，真实 iStoreOS 部署与恢复演练必须作为明确的用户交接步骤。

## 6. 用户流程或调用流程

1. 维护者在 Git 中提交待发布变更，确保工作区干净。
2. 维护者首次创建本地忽略配置，填写 SSH 主机、用户、端口、远端发布目录、备份目录和服务端口；可选填写私钥路径。
3. 维护者从仓库根目录运行单个 PowerShell 部署命令。
4. 脚本完成本地和远端预检并取得远端部署锁；若同一 Git SHA 已由匹配镜像健康运行，则直接成功结束且不改变服务器状态。
5. 非 no-op 部署打包当前 `HEAD` 并上传校验。
6. 服务器在临时目录构建提交 SHA 镜像；已有自动化发布时旧容器继续服务，首次接管时允许旧服务已由维护者停止。
7. 构建成功后脚本停止可识别的旧服务；首次接管不处理配置目录之外的旧 Docker。随后以临时文件生成并原子覆盖唯一数据库备份。
8. 已有自动化发布时脚本保存旧镜像临时引用；首次接管明确记录没有旧版本可自动恢复。脚本随后替换唯一正式发布目录并启动新镜像。
9. 新服务健康时脚本清理临时内容并成功结束。
10. 新服务失败时脚本自动恢复旧镜像和部署前数据库，确认旧服务健康后以失败状态结束。
11. 后续需要历史版本时，维护者从 GitHub/Git 检出目标提交并重新运行同一命令。

## 7. 数据、接口与状态

- **本地配置**：SSH 主机、用户、端口、可选私钥、远端正式发布目录、远端备份目录、服务端口和健康超时；文件必须被 Git 忽略。
- **发布标识**：来源 Git 提交 SHA、派生镜像标签和部署时间，仅用于诊断与当前发布识别。
- **当前发布标记**：正式发布目录中持久化的当前 Git SHA；必须与运行容器镜像和健康状态共同用于幂等判断。
- **源码归档**：只包含 Git `HEAD` 内容；上传后必须校验完整性；属于临时数据。
- **正式发布目录**：自动化管理范围内远端唯一保留的一份当前源码与 Compose 配置；首次接管前的旧目录是用户持有的外部人工回退资产。
- **临时构建目录**：远端部署期间使用，成功或已恢复失败后删除。
- **数据库备份**：用户配置目录中的固定单一文件；新备份通过临时文件原子替换。
- **持久卷**：现有 `home-party-game-platform-data`，自动化不得删除或重命名。
- **镜像状态**：当前提交镜像；部署切换期间的旧镜像临时回滚引用；成功后不要求保留历史回滚标签。
- **部署锁**：远端单写者状态，必须带有足够信息区分有效部署和可安全清理的遗留锁。
- **外部接口**：本地 PowerShell 命令调用 Git、SSH/SCP；远端 shell 调用 Docker Compose、Docker 和文件系统操作。

不新增应用业务 API、数据库业务表或用户账户权限。部署配置不进入 Web 应用运行时状态。

## 8. 异常、边界与恢复

- 本地工作区不干净、提交不存在、工具缺失或配置无效：远端零变更并失败。
- SSH 认证失败、主机密钥失败或远端不可达：不绕过安全检查，远端零业务变更并失败。
- 已有有效部署锁：拒绝并显示锁信息，不启动第二次部署。
- 本地 `HEAD`、远端当前发布标记、运行容器镜像和健康状态一致：以退出码 0 作为 no-op 结束；除短暂取得和释放部署锁外不得改变远端状态。
- 上传或校验失败：删除可安全识别的临时文件，旧服务和备份不变。
- 镜像构建失败：已有自动化发布时旧服务继续运行；首次接管时保持维护者已经停止旧服务的现状。两者的备份和正式发布目录均不变。
- 停服后备份失败：重新启动旧服务并验证健康；不得继续切换。
- 唯一备份替换必须为“新备份验证成功后覆盖”，任何失败不得破坏上一份备份。
- 正式目录替换失败：使用临时旧目录或已记录状态恢复原目录，启动旧服务。
- 新服务健康失败：已有可识别旧版本时恢复旧镜像和部署前数据库；首次接管时停止新服务并恢复部署前数据库，不触碰配置目录之外的旧 Docker。
- 回滚健康失败：停止自动尝试，保留日志和唯一备份，给出人工恢复命令，不删除卷。
- 用户中断：若尚未停服则清理临时内容；若已停服则进入与失败回滚相同的恢复路径。
- 首次部署没有旧容器时：仍必须创建数据库备份规则和健康检查；若没有可回滚旧镜像，失败时停止新服务、保留卷和诊断信息，并明确报告“无旧版本可自动恢复”。
- 固定备份文件被人为删除或目录不可写：部署前拒绝或在停服备份阶段安全失败，不得在无部署前备份的情况下切换。
- 端口、卷名和 Compose 项目名必须稳定，避免新旧发布产生第二套服务或匿名卷。

## 9. 非功能需求

- **NFR-001 数据安全**：任何自动路径不得删除持久卷；切换前必须存在本次有效冷备份。
- **NFR-002 凭据安全**：不得保存或输出密码和私钥内容；必须保留 SSH 主机密钥校验。
- **NFR-003 可恢复性**：已有可识别旧版本时，切换失败必须自动恢复旧镜像与部署前数据库；首次接管无旧版本时必须停止新服务、恢复部署前数据库并进入明确、可诊断的人工恢复状态。
- **NFR-004 可追踪性**：每次镜像和发布必须可映射到唯一 Git 提交。
- **NFR-005 幂等与并发**：同一提交已健康运行时重复部署必须成功 no-op，不得重新上传、构建、备份、重启或覆盖文件；并发部署必须互斥。幂等只约束部署状态，不得重置或回滚服务器运行期间产生的业务数据。
- **NFR-006 空间上界**：正常结束后只保留一个正式发布目录和一个备份文件；临时目录与临时回滚标签不得长期累积。
- **NFR-007 可观察性**：终端必须显示阶段、结果、健康状态和恢复建议，且不泄露敏感数据。
- **NFR-008 兼容性**：本地入口应兼容项目当前 Windows PowerShell 环境；远端只依赖现有 iStoreOS、POSIX shell、Docker 与 Compose 能力。
- **NFR-009 停机时间**：已有自动化发布时，远端构建和上传期间旧服务继续运行，停机只覆盖冷备份和容器切换所需时间。首次接管若维护者已手动停服，自动化不承诺该次接管前的可用性。
- **NFR-010 离线运行边界**：目标应用运行仍不依赖公网；部署过程只依赖维护者选择的 LAN SSH 和已有本地源码，不要求 Docker Registry。

## 10. 初步实现方向与影响范围

- 在仓库中增加本地 PowerShell 编排脚本、远端 POSIX shell 执行脚本和无敏感值的示例配置。
- 调整 Compose 镜像名为可通过环境变量指定的提交标签，同时保持现有默认值、端口、命名卷和 healthcheck。
- 使用 Git 归档生成只含 `HEAD` 的源码包，并生成哈希供远端校验。
- 在远端以固定 Compose project name 构建新提交镜像，构建完成前不修改当前服务。
- 使用 Docker 临时容器访问命名卷完成冷备份和恢复；恢复时处理 SQLite WAL/SHM。
- 使用临时镜像标签保存切换前镜像，成功后删除，失败时用于即时回滚。
- 使用唯一正式目录旁的临时 incoming/previous 路径完成可恢复目录替换，正常结束后清理。
- 增加不连接真实服务器的本地验证夹具或模拟远端命令层，覆盖成功、构建失败、备份失败和健康失败回滚。
- 更新 `deploy/README.md` 和根 README 的一键部署说明。

以上是初步方向，不冻结具体文件名、函数划分或测试命令；后续规划必须根据项目事实选择最小可恢复实现。
