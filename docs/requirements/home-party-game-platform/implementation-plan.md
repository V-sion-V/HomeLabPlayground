## 2. 项目现状与全局实现依据

### 2.1 当前事实

- 工作区仅含需求工作流文档，无 Git 元数据和生产文件；不存在需要保留或协调的用户代码变更。
- 目标规模为约 15 个在线账户、1–2 个活动房间及对应公共大屏，单机单进程服务足以覆盖首版，不需要分布式协调。
- 运行时必须完全本地化；构建时可解析并锁定依赖，生产镜像必须包含服务端、前端静态资源和所有运行依赖。
- 首版没有迁移来源，但从第一版起需要可编号、可重复执行的数据库迁移，以免后续升级直接修改已持久化数据。

### 2.2 技术基线

- 使用 Node.js 24 LTS、TypeScript 和 npm workspaces。Node.js 官方将 24.x 标为 LTS，适合作为生产容器基线；依赖与容器基础镜像在实现时锁定到已验证补丁版本和锁文件。
- 使用 Fastify 提供 HTTP、健康检查、静态资源和 WebSocket 接入；只选择支持 Node.js 当前 LTS 线的稳定版本。
- 使用 React 和 Vite 构建一个响应式单页客户端，玩家端与公共大屏共享协议和公开牌桌组件，但拥有不同路由、投影类型和交互能力。Vite 的生产构建目标覆盖现代主流浏览器，必要兼容项由显式构建目标和浏览器验证控制。
- 使用 SQLite 单文件数据库和成熟的同步 Node.js 驱动。所有权威写入在同一服务进程内串行进入显式事务，匹配 SQLite 单写入者模型；不采用仍处于 release-candidate 稳定级别的 `node:sqlite` 作为首版关键持久化接口。
- 使用 Vitest 覆盖纯领域和持久化集成测试，使用 Playwright 覆盖 Chromium、WebKit、桌面和移动视口的关键用户流程；负载和重启恢复使用进程级集成脚本及 Docker 烟雾验证。

- [Fastify LTS 策略](https://fastify.dev/docs/latest/Reference/LTS/)
- [Vite 浏览器与构建说明](https://vite.dev/guide/)
- [SQLite 事务语义](https://www.sqlite.org/lang_transaction.html)
- [SQLite 原子与持久化保证](https://www.sqlite.org/transactional.html)

### 2.3 预期代码分区与依赖方向

- `apps/server`：进程入口、HTTP/WebSocket 适配器、会话控制权、定时器调度、投影广播、健康检查和静态资源托管。
- `apps/web`：大厅、设置、房间、玩家牌桌、公共大屏、双语、设备偏好、筹码缓存、动画与音效。
- `packages/contracts`：命令、响应、错误码、版本、公开/玩家/大屏投影的共享类型和运行时校验。
- `packages/domain`：账户、赛季、房间、连接租约、资产流水、不变量和与框架无关的状态转换。
- `packages/poker`：两种德州扑克模式、行动合法性、主池/边池、牌型、结算、撤销和自动推进。
- `packages/persistence`：SQLite 迁移、仓储、事务、幂等结果、快照、流水和启动恢复。
- `packages/test-support` 与 `tests`：确定性牌组、时钟、随机源、故障注入、WebSocket 场景、浏览器流程和容量场景。
- `deploy`：多阶段 Dockerfile、Compose 示例、数据卷、健康检查和局域网运行说明。

依赖只能由适配层指向领域层：`apps/* -> contracts/domain/poker/persistence`，`persistence -> domain contracts`，`poker -> domain contracts`。领域和扑克包不得依赖 Fastify、React、SQLite 或浏览器对象。

## 3. 全局详细设计

### 3.1 运行时组件与权威边界

生产形态为一个 Node.js 服务进程和一个 SQLite 数据卷。服务进程托管构建后的 Web 客户端，处理账户进入和健康检查，并通过 WebSocket 接收命令、返回确认、推送按接收者过滤的权威快照。客户端动画、拖动中的筹码和未提交缓存从不写入领域状态。

每个玩家控制连接持有一个服务端签发的随机连接租约。租约不是身份认证，也不得改变免密码账户语义；它只用于保证同一账户只有一个当前控制连接。输入已有用户名会建立新租约并原子失效旧租约。公共大屏使用独立的只读订阅类型，不占账户或座位。

所有改变状态的消息使用统一命令信封：

- `commandId`：设备为一次意图生成并在重试时复用的稳定 ID。
- `connectionId`：当前控制连接租约；公共大屏不能发送写命令。
- `aggregateId`：目标账户、赛季或房间。
- `expectedVersion`：客户端据以发起命令的权威版本。
- `type` 与 `payload`：受运行时 schema 校验的命令类型与内容。

命令结果包含 `accepted`、`rejected` 或 `replayed`、稳定错误码、本地化参数、最新版本和接收者自己的最新投影。重复 `commandId` 返回已保存结果；过期版本、旧租约、错误行动者或非法状态返回拒绝且不得有部分写入。

### 3.2 数据、事务与恢复

SQLite 数据文件固定挂载在 `/data/platform.sqlite`。核心表按以下职责设计：

- 账户、规范化用户名、全局设置、赛季、赛季账户资产和不可变历史排行榜快照。
- 房间、座位、连接租约、房间版本和持久化截止时间。
- 当前游戏快照：公开状态、服务器私有牌堆/手牌状态、行动状态和最近可撤销记录；私有字段只能由服务端投影器读取。
- 资产交易、成对或成组流水、余额物化值、反向交易关系和结果摘要。
- 已处理命令及其确定性结果、数据库迁移版本和待恢复定时动作。

所有权威命令在一次 `BEGIN IMMEDIATE` 写事务中完成：校验租约与版本、检查幂等表、执行纯领域转换、写入资产流水与余额、写入游戏快照和新版本、保存命令结果，然后提交。任一步失败时显式回滚。常规资产交易的流水增量总和必须为零；创建账户或新赛季基础分使用明确的赛季发行类型，并验证发行额恰好等于固定基础分。任何余额写入后都检查非负和赛季总量不变量。

仅筹码模式的错误结算和普通下注撤销都使用引用原交易的补偿流水，不删除历史。可撤销资格保存在权威状态中，并由当前房间版本和下一玩家是否已确认共同判定。

服务启动时先执行向前、编号且可重复的迁移，再在允许服务就绪前完成一致性检查：未完成事务由 SQLite 回滚；持久化的房间快照、资产余额、幂等结果和未来截止时间被重新装载；已到期动作通过新的幂等命令执行。连接本身不持久化，重连后按账户和座位恢复并建立新租约。动画中间帧与下注缓存不恢复。

### 3.3 平台领域

- 用户名以 Unicode 字符串去除首尾空白并进行大小写无关规范化后保持唯一；首版长度上限作为实现常量和双语错误码记录，不改变中文或英文可用性。
- 设备最近账户、界面语言和静音保存在浏览器本地；服务端全局语言仅作为新设备默认值。
- 房间是账户占用和游戏生命周期的边界。加入、开始、暂停、移除、转让、终止和关闭都经过房间版本控制；房主断线截止时间持久化，在线候选人由加密安全随机源选择。
- 赛季切换在单一事务中先验证不存在任何未关闭房间，再固化历史资料和排名快照、关闭旧赛季、创建新赛季及为所有账户发行基础分。任何失败保持旧赛季完整有效。
- 排行榜读取独立的显示值：入桌时保存冻结分数，离桌兑换完成后清除冻结；守恒校验始终读取真实资产账户和牌桌资产。

### 3.4 德州扑克领域

扑克包以纯状态转换函数实现，时间、随机源和持久化由外层注入。共用规则负责按钮和盲注轮转、合法行动、最低加注、全押、行动闭合、贡献分层、主池/边池、资格、平分和不能整除的最小单位。确定性测试可注入牌组和随机序列；生产洗牌使用 Node.js 加密随机字节执行无偏 Fisher–Yates 洗牌。

- 仅筹码模式不创建任何线上牌或公共牌槽；房主只能为每个底池选择仍具资格的赢家，系统计算分配。下一手开始前可用反向流水撤销最近结算。
- 筹码＋牌模式由服务端保存牌堆、烧牌/公共牌进度和每席私有手牌，自动评估标准牌型并按底池资格分配。断线和重连只重投影既有牌局，不重新取随机数。
- 玩家下注撤销和下一玩家命令在同一房间版本上竞争；事务只允许一个先提交的结果。结束下注轮的动作写入至少 3 秒后的自动推进截止时间，截止前仍可撤销。
- 房主移除、无人在线关闭和正常终止都复用“完成或作废当前手牌 -> 处理退款/底池 -> 兑换桌面余额 -> 关闭房间”的事务化领域流程。

### 3.5 投影、客户端与交互

投影器按角色从同一权威快照生成三个不相交的 schema：

- 玩家公开字段加本人的私有手牌。
- 其他玩家的公开状态，不含任何私有手牌或未公开牌堆信息。
- 公共大屏只读公开字段，且仅在筹码＋牌模式包含公共牌槽。

协议测试必须使用字段白名单和负向断言证明隐藏牌不会出现在其他玩家、大屏、错误响应或普通日志中。

Web 客户端提供大厅、设置 modal、赛季确认 modal、房间和牌桌路由。双语文案使用稳定键值，不把服务端自由文本直接展示为错误。筹码栏以 Pointer Events 同时覆盖触控和鼠标，并提供可聚焦的键盘操作；缓存仅存在于当前玩家客户端。收到改变行动权、跟注额、最低加注、可用筹码或暂停状态的较新权威版本时清空缓存并显示原因，普通公开动画更新不清空。

动画由确认事件及服务端时间戳派生，不阻塞命令提交、广播或恢复。自动推进截止时间在界面显示可见倒计时。音效等待首次用户交互解锁并允许设备级静音；播放失败只影响声音，不影响状态机。

### 3.6 错误、隐私与可观察性

- 入口和命令 payload 均执行运行时 schema、范围、状态、租约和版本校验；失败使用稳定错误码及本地化参数。
- 结构化日志记录请求/命令关联 ID、命令类型、聚合 ID、拒绝原因、迁移/持久化结果和不变量状态，不记录牌堆、手牌、连接租约或完整客户端 payload。
- 资产、隐藏牌、历史赛季、构建可启动性和恢复属于硬门禁；即使运行采用 `relaxed` 也不能转为报告项。
- 产品不添加密码、管理员角色或互联网身份。局域网信任假设不削弱服务端角色校验、输入校验、投影隔离和只读大屏约束。

### 3.7 兼容、部署、升级与回退

生产构建将全部 JS、CSS、字体、图标、头像和音效打入本地静态资源，不使用 CDN 或运行时外部服务。多阶段 x86-64 Linux 镜像只保留生产依赖、构建产物和迁移；以非 root 用户运行，暴露一个可配置局域网端口，并提供就绪/存活健康检查。

Compose 示例显式挂载 `/data` 数据卷并记录 iStoreOS 启动方式。首版回退为停止并替换应用容器、保留数据卷；初始建库没有旧格式需要降级。后续任何会改变既有格式的迁移必须先形成向前迁移与备份/恢复约定，不允许旧容器在不兼容 schema 上启动。

## 5. 跨阶段依赖与不变量

路线图只有一个阶段，但任务检查点和任何后续纠正阶段都必须遵守以下全局不变量：

1. 不引入密码、管理员认证或账户所有权验证；连接租约只控制并发连接。
2. 每次资产变化都有同事务流水；常规转移零和，赛季发行可解释，余额永不为负。
3. 隐藏牌只存在于服务端私有状态与持有者投影，不进入公共投影、其他玩家投影或普通日志。
4. 历史赛季快照不可被资料修改、新赛季或当前房间写入更新。
5. 已确认状态由数据库事务、命令幂等结果和持久化截止时间恢复；客户端缓存和动画不成为权威状态。
6. 一个账户最多占用一个房间和一个有效控制租约；一个房间版本上的并发命令只有一个权威顺序。
7. 平台协议不依赖德州扑克专属配置；游戏类型、设置分组和投影扩展点保持显式。
8. P-001 完成前不发布半成品；每个任务检查点至少保持当前已声明的构建/测试范围可运行，最终必须保持容器可启动。

## 6. 最终集成与整体验证流程

验证遵循 `relaxed`：不要求红灯优先，先实现再在结果仍有效的最晚位置运行定向证据。后续任务会触碰共享协议、领域和打包时，允许在最终门禁重跑被其影响的早期检查。

| 验证组 | 证据范围 | 门禁 |
| --- | --- | --- |
| V-001 静态与构建 | 锁文件安装、类型检查、运行时 schema、生产前端/服务端构建、无外部静态资源引用 | hard gate |
| V-002 平台领域 | 账户规范化、无密码进入、资料/历史快照、房间占用、房主转让、赛季切换、排行榜冻结 | core |
| V-003 资产与持久化 | 发行与零和属性、买入/下注/退款/结算/兑换、反向流水、重复/过期/并发命令、故障回滚、重启恢复 | hard gate / core |
| V-004 扑克规则 | 2–10 人行动、最低加注、全押、主池/边池、平分、仅筹码赢家资格与撤销、筹码＋牌发牌/判型/结算 | core |
| V-005 投影与连接 | 新连接接管、重连、版本收敛、玩家/他人/大屏字段白名单、两种模式公共牌差异、日志脱敏 | privacy hard gate / core；日志深度 supplemental |
| V-006 客户端流程 | 中英双语、modal、玩家与大屏、触控/鼠标/键盘筹码缓存、动态按钮、撤销、倒计时、动画和静音 | core；非关键跨浏览器表现 supplemental |
| V-007 容量与隔离 | 15 个账户、2 个活动房间和多个大屏的并发脚本；无串房、私有泄露、重复确认或状态不收敛 | core |
| V-008 Docker 与恢复 | x86-64 生产镜像、离线运行时、健康检查、明确数据卷、容器重启前后状态与资产指纹一致 | hard gate / core |

最终结论只能是：

- `passed`：所有 core、硬门禁和 supplemental 验证通过。
- `passed_with_findings`：所有 core 和硬门禁通过，只有已独立证明不影响交付行为的 supplemental 异常；从 `FND-I-001` 起记录并汇总。

任何 critical/high、安全/隐私、数据完整性、构建/运行、兼容性、未知影响、必需门禁或未独立证明的 core 发现都阻塞完成。

### 8.1 主要风险

### 8.2 技术决策

| ID | 结论 | 原因 | 影响 |
| --- | --- | --- | --- |
| TD-001 | Node.js 24 LTS + TypeScript 单仓库 | 当前 LTS、前后端共享协议、适合小规模单机 WebSocket 服务 | 实现时锁定补丁版本与依赖，不追随未验证的 Current 线 |
| TD-002 | 单进程 Fastify + SQLite 显式事务 | 目标规模小，单写入者可简化资产和版本顺序，部署只需一个容器和数据卷 | 不引入分布式锁；所有写命令经过同一事务执行器 |
| TD-003 | 纯领域状态机 + 角色化投影 + 命令幂等表 | 把规则、网络、持久化和隐私边界分离，并支持确定性恢复测试 | 客户端永远不能提交完整状态或自行结算 |
| TD-004 | `single` + `compact` | 绿色项目无迁移/兼容/外部交接，所有能力共享最终集成门禁 | 阶段内使用三个可恢复任务检查点，不生成未来阶段计划 |
| TD-005 | `relaxed` 验证 | 需求记录的用户明确选择 | 不要求红灯优先；core 与硬门禁仍全部阻塞，supplemental 仅在证明无交付影响后可报告 |
