# 家庭聚会游戏平台：首版需求

- 功能标识：`home-party-game-platform`
- 文档状态：已澄清，可进入独立实现规划
- 创建日期：2026-07-26
- 适用工作流：schema `3.2`

## 1. 背景与目标

本项目是在家庭局域网内运行的聚会游戏平台。它必须为朋友聚会提供一个统一的 Web 入口，使玩家可以通过手机触控或桌面鼠标键盘完成账户进入、房间组织和游戏操作，并可将电视或桌面显示器作为公共大屏。

首版目标是交付可在支持 Docker 的 x86-64 iStoreOS 家庭服务器上运行的统一平台和完整可玩的德州扑克。平台必须同时支持“仅筹码”和“筹码＋牌”两种德州扑克模式，并建立可供后续阿瓦隆、狼人杀及其他游戏复用的账户、房间、赛季、积分、排行榜、实时同步和公共大屏能力。

家庭局域网是唯一目标环境。产品不建立密码、账户所有权验证或互联网威胁模型，但隐藏手牌、积分守恒、并发操作和持久化恢复仍属于游戏正确性的核心要求。

## 2. 范围

### 2.1 包含范围

- 统一的玩家账户、头像、语言选择和免密码进入流程。
- 大厅、房间、房主、座位、在线状态、断线重连和房主转让。
- 玩家模式以及面向电视或桌面显示器的只读公共大屏模式。
- 简体中文和英文界面。
- 全局设置悬浮窗、赛季创建、当前及历史赛季排行榜。
- 以分数为账户资产、以筹码为牌桌资产的守恒型积分经济。
- 2–10 人无上限德州扑克现金桌。
- 仅筹码模式：线下使用实体牌，平台管理庄家、盲注、行动、下注、主池和边池，由房主录入摊牌获胜者。
- 筹码＋牌模式：服务端完成洗牌、发牌、公共牌推进、牌型判定和底池分配。
- 面向触控和鼠标拖动的虚拟筹码下注交互、合法性提示、动画、音效和有限撤销。
- 账户、赛季、房间、进行中对局、资产流水和必要结果摘要的持久化与恢复。
- Docker 化局域网部署，运行时不依赖公网或第三方服务。

### 2.2 不包含范围

- 阿瓦隆、狼人杀及其他游戏的首版规则与界面；首版只保留后续接入能力。
- 公网暴露、安全加固、密码、账户所有权验证、管理员认证或细粒度权限体系。
- 好友系统、在线匹配、机器人、语音或视频、原生 App、观战、成就、付费功能和跨服务器联机。
- 安装型 PWA。
- 单个账户删除、人工调分或在当前赛季中重置个别玩家资产。
- 永久保存完整牌局回放、所有手牌历史或用于争议仲裁的审计产品。
- 首版赛季记录删除或修改。
- 首版数据导入、旧系统迁移和跨架构部署；这是全新空项目。

## 3. 已确认的项目事实与约束

- 工作区在需求澄清开始时完全为空，没有代码、配置、测试、清单、Git 元数据或 `AGENTS.md` 约定。
- 目标服务器为支持 Docker 的 x86 系 iStoreOS（基于 OpenWrt）；首版按 x86-64 容器运行环境约束。
- 平台最多面向约 15 个同时在线账户和 1–2 个同时进行的房间；公共大屏不占玩家名额。
- 所有必要前端资源、游戏逻辑和持久化能力必须由家庭服务器本地提供。
- 首版界面必须支持简体中文和英文，并在手机与桌面浏览器上工作。
- 同一账户同一时间只能参加一个房间；同一账户出现新控制连接时，新连接取代旧连接。
- 无密码和可直接输入已有用户名进入账户是明确的产品行为，不得在实现阶段擅自增加认证门槛。
- 任一实现阶段都必须保持：已确认资产不重复、不丢失；隐藏牌不发送给无权查看的客户端；已完成赛季历史不可被当前赛季操作改写；部署产物保持可启动。
- 当前没有迁移兼容负担。未来接入其他游戏时必须复用平台能力，不得把德州扑克专属配置平铺到不可扩展的全局界面顶层。

## 4. 交付与验证策略

本次运行采用用户明确选择的 **宽松模式（`relaxed`）**。

- 实现可以先于测试证据。
- 每个 `core` 验收项和项目硬性门槛始终阻塞交付。
- 经证明确实不影响交付行为的 `supplemental` 异常可以作为带严重级别的 `FND-*` 报告项保留，而无需为了该异常反复诊断或修复。
- `critical`/`high`、安全或隐私、数据与资产完整性、兼容性、构建或运行、未知影响、必需门槛以及未被独立证明的核心验收发现始终阻塞。
- 不得在失败后把既定 `core` 验收降级为 `supplemental`。

## 5. 功能需求

### 5.1 账户、语言与大厅

- **FR-001** 首次进入平台且当前设备没有最近账户时，系统必须引导用户输入唯一用户名并选择头像，然后自动创建账户并进入大厅，不得要求密码。
- **FR-002** 用户名去除首尾空格后必须按不区分大小写的方式保持全局唯一；输入已有用户名必须直接进入对应账户。设备必须记住最近账户，并允许用户主动切换。
- **FR-003** 首版头像必须从内置头像或 emoji 中选择。用户必须能够修改用户名和头像；当前赛季显示最新资料，历史赛季保留结算时的资料快照。首版不得删除单个账户。
- **FR-004** 玩家端和公共大屏必须支持简体中文和英文。系统必须使用全局默认语言初始化新设备，并允许各设备覆盖并记住自己的语言选择。
- **FR-005** 大厅必须展示等待中的房间、进行中房间的必要公开状态、当前赛季排行榜入口、历史赛季切换入口和角落中的全局设置按钮。

### 5.2 房间、房主与连接状态

- **FR-006** 任何已登录用户必须能够创建或加入等待中的房间。一个账户同时只能进入一个房间；开始对局后不得加入新玩家，只允许原座位玩家重连。
- **FR-007** 房间创建者必须成为房主。房主必须能够转让房主、移除等待中的玩家、开始或暂停对局、终止或重开对局，以及移除对局中已断线的玩家。
- **FR-008** 房主不得查看其他玩家的隐藏牌，也不得任意修改已经确认的隐藏状态或资产。
- **FR-009** 房主断线超过房间使用的可配置时限后，系统必须随机选择同一房间内在线且不是公共大屏的玩家继任。原房主重连后作为普通玩家返回，不得自动取回房主。
- **FR-010** 房主超时且房间内无人在线时，系统必须自动关闭房间。若一手牌尚未结算，该手必须作废并按实际投入原路退款，随后将全部牌桌筹码兑换回各账户分数。
- **FR-011** 轮到断线玩家行动时，首版不得自动超时下注或弃牌；对局必须等待其重连，直到房主暂停、终止或将该断线玩家移除。
- **FR-012** 同一账户的新设备连接必须取得唯一操作权；旧控制连接必须退出玩家席位并得到清晰提示。重复或过期操作不得造成二次下注、二次兑换或状态回退。

### 5.3 公共大屏

- **FR-013** 大厅或房间必须提供“打开公共大屏”入口。公共大屏不得要求账户，不得获得游戏操作能力，不占玩家名额，并允许同一房间存在多个同步大屏。
- **FR-014** 公共大屏必须只展示公开牌桌信息，包括玩家位置与公开状态、数字形式的筹码量和下注额、底池、当前阶段和必要行动提示；不得展示任何玩家手牌。
- **FR-015** 在筹码＋牌模式中，公共大屏必须显示五个公共牌槽位，已发牌正面展示、未发牌显示牌背。在仅筹码模式中，公共大屏不得显示公共牌或空牌槽。
- **FR-016** 玩家确认下注时，公共大屏必须播放筹码从对应玩家方向飞入牌桌的动画；动画结束后必须以数字呈现已下注额和底池。

### 5.4 全局设置、赛季与排行榜

- **FR-017** 大厅角落的全局设置必须使用当前页面上的悬浮窗（modal），不得打开新的全屏页面或浏览器窗口。
- **FR-018** 全局设置悬浮窗顶部必须依次显示默认界面语言和默认房主转让时限。其后必须使用可收起的、带“德州扑克”分割标题的游戏配置区展示默认大小盲、最低买入和最高买入；未来游戏必须使用自己的可收起分组，避免顶层臃肿。
- **FR-019** 任何已登录用户都必须能够打开全局设置和触发“开始新赛季”，不得引入管理员密码或额外身份。
- **FR-020** “开始新赛季”必须弹出确认悬浮窗，并在其中填写新赛季名称和基础分、展示资产重置及排行榜归档影响，再要求最终确认。赛季名称缺省时必须生成顺序名称，例如“赛季 1”。
- **FR-021** 只要存在任何未关闭房间，系统就必须禁止开始新赛季，并说明必须先关闭全部房间、完成筹码兑换。不得通过赛季操作强制终止进行中的牌局。
- **FR-022** 新赛季开始时，系统必须把上一赛季的最终用户名、头像、分数、名次和结束时间保存为不可修改的历史快照，并为所有既有账户初始化新赛季基础分。当前赛季中新增账户必须获得该赛季固定的基础分。
- **FR-023** 排行榜顶部必须显示赛季名称，并允许在当前赛季及全部历史赛季间切换。排行榜必须显示名次、头像、用户名、当前或最终分数和必要的“游戏中”状态，不得显示相对基础分净赚取值。
- **FR-024** 玩家进入牌局时，排行榜必须冻结该玩家进入前的账户分数；买入、补充筹码及牌局内输赢不得实时改变显示。玩家正常退出、被移除或房间关闭并完成兑换后，排行榜必须更新为新的账户分数。

### 5.5 分数、筹码与守恒

- **FR-025** 首个赛季的默认基础分必须为 `10,000`。每个赛季的基础分在该赛季创建时固定，且 `1 分` 必须兑换为 `1 筹码`；所有分数和筹码均为非负整数。
- **FR-026** 买入必须把价值从账户分数原子转移到牌桌筹码；下注必须从牌桌筹码转入玩家当前下注或底池；结算必须从底池转入获胜者牌桌筹码；退出必须把剩余牌桌筹码原子兑换回账户分数。
- **FR-027** 在一个赛季存续期间，账户分数、牌桌筹码、当前下注和底池的全局总和，除新账户获得本赛季基础分外，必须保持不变。新赛季是新的守恒边界，旧赛季先归档，新赛季再按其基础分初始化。
- **FR-028** 系统不得允许透支、赠送、人工调分、删除单个账户或未记录的资产创建与销毁。每次会改变资产归属的确认操作必须产生可追溯的原子流水。
- **FR-029** 已完成对局必须保留结果摘要和资产流水，但首版不要求保存完整操作回放或永久手牌历史。

### 5.6 德州扑克房间与通用规则

- **FR-030** 德州扑克必须支持 2–10 名玩家的无上限现金桌。房主创建房间时必须能够配置“仅筹码”或“筹码＋牌”模式、大小盲、最低买入、最高买入和房主转让时限，并以全局设置作为初始默认值。
- **FR-031** 游戏引擎必须管理庄家按钮轮转、大小盲、行动顺序、过牌、跟注、下注、加注、弃牌、全押、主池、边池、平分底池和合法行动约束。
- **FR-032** 玩家必须在配置范围内选择买入，且不得超过账户可用分数。玩家只能在两手牌之间主动补充筹码或正常退出，补充后不得超过牌桌上限。
- **FR-033** 玩家在一手牌中被房主移除或被迫退出时必须立即弃牌；其已经确认投入的筹码继续留在对应底池，尚未投入的剩余筹码必须兑换回账户分数。
- **FR-034** 房主正常结束牌桌时，必须先完成或作废当前手牌，再把所有剩余牌桌筹码兑换回对应账户分数并关闭房间。

### 5.7 仅筹码模式

- **FR-035** 仅筹码模式必须由线下实体牌承担洗牌、发牌、手牌和公共牌；玩家端与公共大屏均不得录入、显示或预留线上公共牌区域。
- **FR-036** 平台仍必须管理庄家、盲注、行动顺序、下注合法性、主池、边池和各玩家可参与的底池。
- **FR-037** 摊牌时，房主必须为每个待分配底池选择一个或多个符合资格的获胜者；系统必须自动平分并处理不能整除的最小单位，然后向所有客户端展示结果。
- **FR-038** 房主在下一手开始前必须能够撤销仅筹码模式中最近一次错误的手牌结算；撤销必须通过反向流水恢复原状态且不得破坏总量守恒。下一手开始后不得撤销旧结算。

### 5.8 筹码＋牌模式

- **FR-039** 服务端必须负责安全随机洗牌、按座位发出仅本人可见的手牌、推进翻牌/转牌/河牌以及在摊牌时比较标准德州扑克牌型。
- **FR-040** 服务端必须根据弃牌、全押及边池资格自动确定各底池获胜者和分配额。玩家、房主和公共大屏只能收到各自应见的信息。
- **FR-041** 刷新、断线重连或打开新的公共大屏不得重新洗牌、重复发牌、暴露不应公开的牌或改变已确认牌局状态。

### 5.9 玩家端下注交互

- **FR-042** 玩家端不得以“输入数字＋提交按钮”作为下注方式。屏幕底端必须显示一组可横向滑动的现实常用筹码面值：`1`、`5`、`25`、`100`、`500`、`1,000`、`5,000`、`10,000`。玩家必须自行组合合法金额，不得生成自创面值。
- **FR-043** 虚拟筹码栏必须是固定金额选择器，不代表实际筹码库存，不需要找零，也不得随玩家实际资产增减而更换面值。加入当前缓存后会超过剩余可下注金额的面值必须灰显且不可操作。
- **FR-044** 玩家必须能通过触控或鼠标把筹码向前拖入下注缓存区，并看到筹码飞向桌面的动画。玩家端只有下注缓存区持续渲染具体筹码，手中资产、已下注额、其他玩家筹码和底池必须使用数字。
- **FR-045** 玩家必须能够把缓存筹码向后拖回、点击单枚缓存筹码移除，或一键清空缓存。仅在轮到该玩家时允许编辑缓存。
- **FR-046** 当缓存金额合法时，确认按钮必须根据结果显示“跟注”“下注”或“加注”；确认后必须播放筹码推入已下注区域的动画。当金额不合法时，按钮必须禁用并显示原因。
- **FR-047** 玩家端必须提供独立的“弃牌”和“一键跟注/过牌”操作。“一键跟注”只把所需金额放入缓存，仍需确认；无需跟注时执行过牌。必须提供“一键全押”，先把金额放入缓存，再由玩家确认。
- **FR-048** 若服务端确认的牌局变化使当前缓存基于过期的跟注额、最低加注额、可用筹码或行动权，客户端必须清空缓存并明确提示。典型情况包括上一名玩家成功撤销、重连后发现更新状态、房主暂停或服务端拒绝并发操作；普通渲染更新不得无故清空缓存。
- **FR-049** 桌面端必须支持鼠标完成全部下注操作，并允许键盘选择筹码面值、加入或移除缓存、清空及确认，但不得因此引入自由数字输入。

### 5.10 撤销、自动节奏、动画与音效

- **FR-050** 玩家确认一次跟注、下注、加注或全押后，只要下一名玩家尚未确认操作，该玩家必须能够自行撤销刚才的操作。撤销必须恢复筹码和行动权；下一名玩家一旦确认操作，撤销立即失效。
- **FR-051** 撤销与下一名玩家操作发生并发时，服务端必须只接受先被原子确认的一项，拒绝另一项并要求客户端刷新权威状态。
- **FR-052** 若某次操作将结束当前下注轮，系统必须在自动推进下一阶段前提供至少 3 秒的可见等待和撤销机会。
- **FR-053** 对任何会自动改变用户可见游戏阶段或使撤销机会失效的默认操作，系统必须先提供短暂、清晰的视觉等待，并播放对应提示音。至少包括新一手开始、自动发公共牌、进入摊牌、分配底池和开始下一手；心跳、持久化和无用户可见影响的内部操作不得被人为延迟。
- **FR-054** 音效必须支持设备级静音并记住选择，不得依赖背景音乐。受浏览器自动播放限制时，系统必须在用户首次交互后启用音效，不得因此阻塞游戏。

### 5.11 持久化与结果

- **FR-055** 账户、资料、全局设置、赛季、排行榜快照、房间配置、已确认牌局状态、资产流水和必要结果摘要必须持久保存。
- **FR-056** 页面刷新、短暂网络中断和服务重启后，系统必须恢复最近已确认状态和原座位，不得把未确认的客户端缓存当作下注。
- **FR-057** 进行中任务的恢复必须以服务端权威状态和原子流水为准。崩溃发生在资产操作中间时，恢复结果必须是完整提交或完整回滚，不得出现部分兑换。

## 6. 用户流程或调用流程

### 6.1 首次与后续进入

1. 用户打开局域网页面。
2. 若设备存在最近账户，系统优先展示该账户并允许一键进入或切换。
3. 若无最近账户，用户输入用户名并选择内置头像或 emoji。
4. 系统创建账户，发放当前赛季基础分并进入大厅。
5. 用户可输入已有用户名直接进入对应账户，无密码或所有权验证。

### 6.2 创建并加入牌局

1. 用户在大厅创建德州扑克房间。
2. 创建悬浮层从全局默认值初始化模式、盲注、买入范围和房主转让时限。
3. 房主确认房间；其他用户从等待房间列表加入并选择买入。
4. 满足至少两名玩家及配置合法等条件后，房主开始对局。
5. 需要公共大屏时，任一用户从房间打开只读大屏入口。

### 6.3 一次下注

1. 服务端通知轮到的玩家及当前合法操作范围。
2. 玩家横向浏览现实筹码面值，把所需筹码拖入缓存，或使用一键跟注/全押填充缓存。
3. 客户端依据权威状态显示动态按钮和合法性；服务端在提交时再次校验。
4. 玩家确认后，服务端原子记录操作并广播新状态。
5. 玩家端播放筹码推入动画，公共大屏播放筹码从对应座位飞入动画。
6. 在下一名玩家确认前，原玩家可撤销符合条件的操作；若该操作结束下注轮，系统至少等待 3 秒再自动推进。

### 6.4 退出、踢出与恢复

1. 正常退出或补充筹码只能在两手牌之间进行。
2. 对局中断线时，座位保留并等待重连。
3. 房主可移除断线玩家；该玩家自动弃牌，已下注额保留，剩余筹码兑换回分数。
4. 房主掉线超时后，有在线玩家则随机转让；无人在线则作废未结算手牌、退款、兑换并关闭房间。
5. 页面刷新、网络恢复或服务重启时，客户端重新获取服务端权威状态。

### 6.5 开始新赛季

1. 任一已登录用户打开大厅角落的全局设置悬浮窗。
2. 用户点击“开始新赛季”。
3. 若存在任何房间，系统阻止操作并提示先关闭房间、完成兑换。
4. 无房间时，系统弹出新赛季确认悬浮窗，要求填写赛季名称和基础分，并说明影响。
5. 用户最终确认后，系统原子归档旧排行榜，创建新赛季，为所有既有账户设置新基础分并显示新排行榜。

## 7. 数据、接口与状态

### 7.1 核心数据

- **账户**：稳定 ID、规范化用户名、显示用户名、头像、最近更新时间。
- **设备偏好**：最近账户、界面语言、音效静音；设备本地保存，服务端不得将其视为身份凭证。
- **全局设置**：默认语言、默认房主转让时限、按游戏分组的默认房间配置。
- **赛季**：稳定 ID、名称、基础分、状态、开始时间、结束时间。
- **赛季账户资产**：账户、赛季、可用分数、是否正在牌局、排行榜冻结分数。
- **历史排行榜快照**：赛季、名次、账户 ID、结算时用户名、头像和最终分数。
- **房间**：稳定 ID、游戏类型、模式、状态、房主、配置、创建时间。
- **座位**：房间、账户、座位序号、连接状态、买入、牌桌筹码和排行榜冻结分数。
- **牌局状态**：手牌编号、庄家、阶段、轮到玩家、公共状态、私有手牌引用、牌堆状态、当前下注、主池和边池。
- **资产流水**：稳定操作 ID、赛季、账户、房间、手牌、来源、去向、金额、原因、正反向关系和确认时间。
- **结果摘要**：手牌或房间结果、参与者、分配额和完成时间，不要求完整回放。

### 7.2 权威边界与接口行为

- 服务端是账户、房间、牌局、合法行动、牌、资产和赛季的唯一权威。
- 客户端下注缓存、拖动状态和动画是暂存 UI，不是已确认资产。
- 每个改变权威状态的客户端命令必须带稳定的幂等标识和其基于的状态版本。
- 服务端必须拒绝过期、重复、越权于当前行动者或违反规则的命令，并返回最新权威状态及用户可理解原因。
- 实时更新必须按接收者过滤；手牌只能发送给持有者，公共大屏只能收到公开投影。
- 排行榜显示值与资产守恒账本是不同视图：游戏中玩家的排行分数被冻结，但守恒校验始终计算其账户分数、牌桌筹码、下注和底池。

### 7.3 主要状态

- 房间状态至少包括：`waiting`、`in_progress`、`paused`、`closing`、`closed`。
- 手牌阶段至少包括：等待开始、盲注、翻牌前、翻牌、转牌、河牌、摊牌、分配、完成或作废。
- 连接状态至少区分：在线控制连接、被新设备取代、短暂断线和公共大屏。
- 赛季状态至少包括：当前、历史；同一时刻只能有一个当前赛季。
- 资产操作必须与流水在同一原子边界内提交。

## 8. 异常、边界与恢复

- 用户名为空、规范化后重复或超出合理长度时，系统必须拒绝并提供本地化提示；具体长度上限可在规划中选择，不得影响 Unicode 中文和英文名称。
- 买入不足、超出上限、透支、非法下注、低于最低加注、错误行动者或过期状态必须被服务端拒绝，且不得改变资产。
- 同一账户多设备同时操作时，只有当前控制连接有效；旧连接操作必须失败并回到大厅。
- 下注确认和撤销并发时只允许一个原子结果，客户端必须收敛到服务端状态。
- 上一玩家撤销导致跟注额变化、重连发现状态变化或房间暂停时，未提交缓存必须清空并解释原因，避免把旧金额误投到新局面。
- 牌局中玩家断线不会自动弃牌；房主移除后才按强制退出规则处理。
- 房主掉线超时且无人在线时，未完成手牌作废、投入原路退款、全部余额兑换后关闭房间；失败重试不得重复退款。
- 服务重启必须恢复最近已确认牌局、计时等待和连接可重建状态；客户端动画无需恢复为中间帧。
- 开始新赛季时若存在任一房间，操作必须失败且不得局部归档、重置或修改任何资产。
- 新赛季创建必须是原子操作：旧赛季完整归档且新赛季完整初始化，或者全部保持旧状态。
- 历史赛季资料是快照，后续账户改名或换头像不得改写历史。
- 浏览器阻止自动播放时，游戏必须继续，首次用户交互后再启用声音。
- 仅筹码模式出现错误获胜者录入时，只能在下一手开始前通过结算反向流水恢复；下一手开始后不得修改历史结算。
- 当前赛季没有账户时，总量为零；新增账户增加恰好一个本赛季基础分。跨赛季重置属于新守恒边界，不与上一赛季总量直接比较。

## 9. 非功能需求

- **NFR-001 响应式交互**：玩家端必须适配常见手机竖屏触控和桌面鼠标键盘；主要操作不得依赖 hover。
- **NFR-002 实时性**：在目标局域网和规模内，已确认操作应及时同步到所有相关玩家和公共大屏；动画不得阻塞服务端确认或下一次状态恢复。
- **NFR-003 容量**：系统必须支持最多约 15 个同时在线账户和 1–2 个同时进行的房间，并容纳对应公共大屏连接。
- **NFR-004 浏览器**：首版必须支持当前主流 Chrome、Edge、Safari 以及 Android 系主流浏览器。
- **NFR-005 离线运行**：部署完成后，核心运行不得依赖公网、CDN、外部身份、云数据库或第三方实时服务。
- **NFR-006 部署**：必须提供适用于 x86-64 iStoreOS Docker 环境的非交互式启动方式和持久化数据卷约定。
- **NFR-007 恢复**：服务进程重启不得破坏已确认资产、赛季、房间或牌局状态。
- **NFR-008 本地化**：所有用户可见的固定文本、错误、按钮和关键音效语义必须可在简体中文与英文间切换。
- **NFR-009 游戏隐私**：尽管不建立安全威胁模型，服务端仍不得把隐藏手牌放入公共状态或发送给其他玩家与公共大屏。
- **NFR-010 可扩展界面**：全局设置和大厅游戏入口必须能按游戏分组扩展，增加阿瓦隆或狼人杀时不得要求重做平台级账户、房间、赛季和排行榜接口。
- **NFR-011 可观察性**：服务端应记录足以诊断启动失败、持久化失败、被拒绝操作和资产不变量异常的结构化日志，不得把隐藏牌写入普通日志。
- **NFR-012 动效节奏**：自动阶段推进必须留出人类可感知的等待和提示音；音效可静音，动画状态不得成为规则或资产状态的唯一载体。

## 10. 初步实现方向与影响范围

以下内容是需求阶段的初步方向，不构成详细技术设计或阶段路线图：

- 使用一个可在 iStoreOS Docker 中运行的本地服务，提供前端静态资源、实时双向状态同步和持久化 API。
- 使用服务端权威房间/牌局状态机，将公开投影、玩家私有投影和公共大屏投影分开。
- 使用本地嵌入式持久化存储保存账户、配置、赛季、房间、快照和资产流水；具体数据库与框架由后续规划根据 iStoreOS 约束确定。
- 把积分经济实现为原子双向流水，而不是直接散落修改余额；以稳定命令 ID 处理重试和并发。
- 将平台层与德州扑克规则模块分开；平台层拥有账户、房间、连接、赛季、排行榜、国际化和展示入口，游戏模块拥有规则、状态、动作和游戏专属设置。
- 玩家端和公共大屏可复用实时连接与公开牌桌组件，但必须使用不同权限投影和布局。
- 验证影响覆盖账户恢复、并发控制、资产守恒、赛季原子切换、扑克规则与边池、私有牌隔离、触控/鼠标交互、双语和 Docker 重启恢复。
- 因为项目为空，不需要迁移；部署回退必须至少能够停止新容器并保留持久化数据卷，数据格式升级策略由后续规划在首次定型前明确。

跨阶段不变量：

1. 任意中间阶段不得引入密码或改变免密码账户语义。
2. 资产改变必须由原子流水支持，且在赛季边界内满足总量守恒。
3. 隐藏牌不得进入不相干玩家或公共大屏投影。
4. 完成的历史赛季不得被当前资料、设置或新赛季改写。
5. 已确认状态必须可在刷新、重连和服务重启后恢复。
6. 每个可部署中间状态必须保持容器可启动或被明确标记为尚未进入生产文件变更阶段。
