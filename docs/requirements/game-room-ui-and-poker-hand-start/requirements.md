# 游戏房间界面统一与德州扑克开手体验：需求

## 1. 背景与目标

当前平台已经完整支持德州扑克与阿瓦隆，但两种游戏的玩家房间顶栏、房间准备区、
玩家状态强调、公共大屏入口和移动端布局仍有不一致；德州扑克还会在开手时自动扣除
大小盲并常态显示本人底牌，下注缓存占用底部操作区且拖动手势会妨碍手机横向滚动。

本功能面向可信家庭局域网内的房主、参赛者、房间观战成员和匿名公共大屏，目标是：

1. 统一两种游戏所有已登录房间页面的顶栏信息与操作层级。
2. 压缩并重排阿瓦隆准备区，在玩家端和匿名大屏清晰、实时地展示角色构成。
3. 让德州扑克开手先进入服务端权威的手动盲注与底牌确认阶段，两种模式均不再自动
   下盲注。
4. 默认遮盖线上底牌，只允许本人通过按住操作临时查看。
5. 把下注缓存改为只在本人回合出现的牌桌悬浮卡片，移除下注拖动并修复手机牌桌裁剪。

服务端仍是房间、游戏阶段、盲注、确认、资产和秘密投影的唯一权威。任何界面状态、
动画、悬浮卡片或本机按住状态都不得替代服务端校验。

## 2. 范围

### 2.1 包含范围

- Poker 与 Avalon 的已登录等待、参赛和房间观战页面共用一致的顶栏结构。
- 房间内移除公共大屏入口；大厅房间卡继续提供匿名公共大屏入口。
- Poker 与 Avalon 不再向用户提供暂停、恢复或手动作废功能。
- 阿瓦隆准备卡与房主设置卡改为上下排列；准备卡压缩高度并展示实时角色构成。
- 阿瓦隆房间名区域提供角色构成浮层；匿名大屏改为持续显示角色构成卡。
- 阿瓦隆 300px 手机视口的“本局参赛”玩家卡保持双列。
- Poker 玩家卡使用操作提示填充表示当前行动或待完成开手动作，并用独立边框标记本人。
- 两种 Poker 模式都增加手动盲注与全员开手确认；筹码＋牌显示线上底牌，纯筹码模式
  确认已拿到线下实体底牌。
- Poker 在线底牌从牌桌常态区域移除，改为本人按住“查看底牌”时临时显示。
- Poker 下注缓存改为只在本人回合出现的半透明牌桌悬浮卡；筹码列表只支持点击、触控
  和键盘操作，不再支持拖入、拖回或其他下注拖动。
- Poker 手机玩家卡、庄家标识、阴影、公共牌尺寸和边界修复。
- 为上述行为所必需的共享契约、Poker 状态、命令、服务投影、SQLite 快照兼容和测试。

### 2.2 不包含范围

- 不新增游戏类型、角色、扑克变体、机器人、聊天、音视频、密码或公网身份。
- 不改变 Poker 翻牌前正式行动开始后的下注、加注、撤销、全押、边池、判型和结算规则。
- 不改变 Avalon 角色规则、秘密知识、投票、任务、刺杀、押分或结算规则。
- 不重设计大厅；只保留并验证现有房间卡公共大屏入口。
- 不新增管理员设置、在线角色配置、远程资源、运行时依赖或 SQL 业务表。
- 不修改部署自动化，不执行正式 `home-table` 发布；正式发布继续需要独立授权。
- 不改写既有 `home-party-game-platform`、`poker-room-experience-upgrade` 或
  `avalon-game` 的冻结需求、计划、结果和修改记录。

## 3. 已确认的项目事实与约束

1. 项目是 npm workspaces 管理的 TypeScript ESM 单仓库；相关实现位于
   `apps/web`、`apps/server`、`packages/contracts`、`packages/domain`、
   `packages/poker` 和 SQLite 持久化边界。
2. 当前 `PokerState` 已有 `blinds` 阶段，但 `createPokerState` 会立即自动扣除大小盲、
   发牌并进入 `preflop`；现有状态没有盲注提交者或底牌确认者集合。
3. 当前 Poker 玩家投影只向有效控制租约下的本人提供 `ownHoleCards`，匿名大屏、观众、
   其他玩家和普通日志不含私牌；Web 玩家牌桌目前会常态渲染该字段。
4. 当前盲注流水在开手后立即记录。新协议必须保持每笔实际盲注仅记录一次、牌桌筹码与
   底池守恒、短额大盲仍维持完整大盲开局跟注额。
5. 当前 Avalon 房间公开配置包含 5–10 人角色预设或房主自定义角色列表，因此角色
   **构成**可以公开派生；活动期每个角色具体分配给谁仍是秘密。
6. 当前大厅的 Poker 与 Avalon 房间卡均已有“打开公共大屏”链接，因此房间内入口可以
   移除而不丢失公共大屏能力。
7. 当前 `room.pause`、`room.resume` 与 `avalon.void` 是外部命令，Avalon 的安全关闭、
   活动参赛者离开/移除等路径还会在内部自动作废并退款。用户取消的是直接暂停、恢复和
   手动作废能力，不得取消为保护资产与秘密所必需的内部安全作废。
8. SQLite 使用 WAL、版本化 JSON 快照和 `processed_commands`。新的已确认盲注、
   确认集合和阶段必须原子持久化；本机下注缓存、角色构成浮层开关和按住显示状态不得
   持久化。
9. 现有活动手牌、旧快照、账户、赛季、房间、排行榜、流水、公共大屏、Docker `/data`
   卷和部署接口必须兼容；升级不得重复发牌、重复扣盲注或静默改写资产。
10. 全部新增文案与状态必须支持简体中文和英文，并在桌面、当前主流浏览器、键盘、
    触控和 300px 动态视口下可用；关键信息不得只依赖颜色、hover 或动画。
11. 产品仍只适用于可信家庭 LAN。该信任边界不放宽隐藏牌、Avalon 秘密、资产守恒、
    并发、控制租约、只读大屏、持久化或恢复要求。

## 4. 交付与验证策略

- 本次 initial 运行采用用户明确选择的 `relaxed` 策略。
- 实现可以先于测试，但全部 `core` 验收、隐私、资产完整性、旧快照兼容、构建能力和
  项目硬门禁仍是阻塞项。
- 只有已经独立证明不影响交付行为的 `supplemental` 异常，才可以保留为带严重程度的
  `FND-I-*` report-only finding；未知影响、严重程度为 critical/high、隐私、资产、
  兼容、构建/运行或 core 验收异常不得报告后放行。
- 验收层级在执行失败后不得为了完成运行而降级。

## 5. 功能需求

### 5.1 共用房间顶栏与房间级操作

**FR-001** 所有已登录 Poker/Avalon 等待、参赛和房间观战页面必须使用相同的三段式
顶栏：

- 左侧依次为“返回大厅”和“离开房间”；
- 中间显示房间名称、本地化游戏名称和当前权威阶段；
- 右侧只有房主显示“关闭房间”，非房主右侧为空。

顶栏不得再显示当前登录玩家、公共大屏入口或其他游戏操作。

**FR-002** 桌面端“返回大厅”和“离开房间”必须显示图标与文字；手机端必须变为两个
圆形图标按钮，并保留本地化可访问名称、焦点样式和足够触控目标。关闭房间仍是独立的
危险操作，并沿用确认与服务端授权。

**FR-003** “返回大厅”只切换视图而不离开房间；“离开房间”和“关闭房间”继续遵守
各游戏现有成员、参赛、资产、房主转让与确认语义。房间内不得提供公共大屏链接，大厅
房间卡必须继续能够匿名打开对应只读大屏。

**FR-004** 顶栏阶段必须来自权威房间/游戏状态，并以中英文区分至少等待准备、盲注与
开局确认、各 Poker 街道、完整结算，以及 Avalon 的认角色、夜间、提名、投票、任务、
刺杀和结算。长房间名不得挤出两侧操作。

**FR-005** 当前 Web 产品不得提供 Poker 或 Avalon 的暂停、恢复、手动作废按钮、菜单
或其他可见入口。受支持的外部命令不得再允许客户端新建 `paused` 状态或手动作废
Avalon 本局；旧命令可以删除或确定性拒绝，但不得产生部分状态。内部因关闭房间、活动
参赛者离开/移除、账户删除或安全恢复而执行的自动作废、退款和秘密保护必须保留。

### 5.2 阿瓦隆准备、角色构成与移动布局

**FR-006** 所有已登录玩家和观战成员必须看到同一宽度、同一结构的房间准备卡。房主在
准备卡下方额外看到独立的“阿瓦隆设置”卡；两卡必须上下排列，不得在宽屏并排。
非房主不得看到或操作设置卡。准备、取消准备、开始和保存配置的现有服务端权限不变。

**FR-007** 准备卡必须移除“房主自动准备并参赛”可见文字和可见的 `x/5–10` 数字，
缩短空白和整体高度。十个圆点继续从左表示当前选中参赛人数，前五个空位为必需、后五个
为空余容量；屏幕阅读器仍必须获得当前人数、最少 5 人和最多 10 人的等价语义。

**FR-008** 准备卡标题下方必须显示当前角色构成：

- 当前选中人数少于 5 时显示“至少5人参与游戏”及等义英文；
- 管理员人数预设模式在 5–10 人时显示该人数对应的完整角色多重集合；
- 自定义模式显示保存的自定义角色多重集合；当前选中人数不兼容时必须同时显示明确的
  人数不匹配提示，不得让错误只在点击开始后才不可理解地出现；
- 准备阶段按“房主 + 当前在线且已准备的非房主成员”实时刷新；
- 活动局和完整结算显示该局冻结参与人数与配置对应的角色构成，不随观战成员加入变化。

角色构成只说明有哪些角色及重复数量，不得显示任何角色分配给哪个账户。

**FR-009** Avalon 已登录房间顶栏的房间名区域必须是可聚焦、可触控的整体按钮式入口，
并在房间名下方显示“点点点”图标。点击、Enter 或 Space 打开角色构成浮层；再次触发、
Escape、外部点击、离房或权威房间切换后关闭。浮层必须显示与 FR-008 相同的当前构成，
不得泄露具体角色归属。

**FR-010** Avalon 匿名公共大屏不得提供房间名点击交互或“点点点”提示；它必须在
“本局参赛”区域上方新增一张持续可见的角色构成卡，并按 FR-008 的等待、活动和结算
规则实时更新。该卡仍属于匿名只读公开投影，不得提供玩家操作。

**FR-011** 300px 及常见手机竖屏下，“本局参赛”中的玩家卡必须保持双列，使用更紧凑
但可读的头像、名称、状态和徽标布局；不得退化为单列、产生页面横向溢出或使长按/右键/
键盘房主管理菜单不可用。

### 5.3 德州扑克玩家状态用色

**FR-012** Poker 当前正式行动者的整张玩家卡必须使用 Poker 操作提示色填充，而不再
只改变边框。开手确认阶段中尚未完成必需动作的玩家也必须使用同一操作提示填充：

- 大小盲未提交盲注时属于未完成；
- 已提交盲注但尚未确认底牌时仍属于未完成；
- 非盲注玩家尚未确认底牌时属于未完成；
- 完成本人全部必需动作后恢复普通背景。

该公开完成状态必须同步到其他玩家、房间观战成员和匿名公共大屏，但不得包含私牌。

**FR-013** 已登录 Poker 参赛者的本人玩家卡必须使用不同于操作提示填充的独立语义色
边框。本人恰好是当前行动者或待确认者时，操作提示背景与本人边框必须同时存在。匿名
大屏没有“本人”状态。行动、本人和已确认状态还必须有文字、ARIA 或其他非纯颜色语义。

### 5.4 德州扑克手动盲注与开手确认

**FR-014** 房主开始首手或下一手后，两种 Poker 模式都必须先进入持久化的开手确认
阶段，不得在建手时自动扣除盲注，也不得在所有必需动作完成前设置正式翻牌前行动者。
庄家、小盲、大盲、冻结参与者、面值和（筹码＋牌模式的）洗牌/底牌必须由服务端一次性
权威确定。

**FR-015** 大小盲玩家最初必须看到位于牌桌上方高层级的开手卡，内容为“你是小盲注，
请下注”或“你是大盲注，请下注”及等义英文，并提供一个盲注按钮。按钮必须原子提交该
玩家固定的配置盲注，短码时提交全部剩余筹码；它不得打开下注缓存、允许选择金额或支持
撤销。短额大盲后正式开局的 `currentBet` 仍必须保持完整大盲。

**FR-016** 小盲和大盲可以任意顺序独立提交，非盲注玩家可以并行完成自己的开手确认；
不得要求某一客户端串行主持。盲注实际提交成功后必须恰好记录一次桌上筹码到底池流水，
重复、过期、并发或失败命令不得二次扣款或留下部分状态。

**FR-017** 筹码＋牌模式中：

- 非盲注玩家进入开手阶段即看到只含本人两张底牌的悬浮开手卡和“确认底牌”按钮；
- 大小盲玩家必须先成功提交盲注，随后同一卡切换为本人底牌与“确认底牌”按钮；
- 确认只记录本人已确认状态，不改变牌、筹码或底池；
- 其他玩家、房主特权、观战成员和匿名大屏不得取得该底牌内容。

**FR-018** 纯筹码模式执行完全相同的手动盲注门禁，但不生成、存储或投影线上底牌。
非盲注玩家进入开手阶段、大小盲成功提交后，必须看到“确认已拿到实体底牌”及等义英文
按钮。该确认代表线下发牌已就绪，不得伪造线上牌面。

**FR-019** 只有当当前仍在手牌中的所有冻结参与者都完成其必需盲注和确认后，服务端才
能原子进入 `preflop`、设置首个合法行动者并广播正式开局。客户端不能仅凭本机计数提前
开始。已确认者恢复普通玩家卡背景，未完成者继续使用 FR-012 的操作提示背景。

**FR-020** 开手确认不设倒计时、自动下注、自动确认或断线代操作。玩家断线时权威状态
无限等待；重连/接管恢复同一牌、盲注和确认进度。房主可以使用现有移除或关闭房间能力
解除阻塞：

- 移除仍按活动手牌语义强制弃牌，已投入盲注留在底池，剩余筹码兑换，并安全选择后续
  行动或结算；
- 关闭房间按现有安全作废、退款、兑换和秘密清理语义执行；
- 当前参赛者不得借普通离房绕过已投入盲注或阻塞规则。

### 5.5 德州扑克底牌临时查看

**FR-021** 筹码＋牌模式的牌桌主体不得常态显示本人底牌；牌桌中心只显示公共牌区域、
阶段/手数、底池和适用的权威倒计时。匿名大屏、房间观战和其他玩家的私牌边界不变。

**FR-022** 原底部“暂停牌局”位置必须改为本人“查看底牌”按钮。该按钮只在本人属于
当前筹码＋牌活动手牌且服务端已经向本人投影底牌时出现；纯筹码模式、匿名大屏和观战
成员不得出现该按钮。

**FR-023** 按住“查看底牌”时，屏幕中央高层级悬浮卡显示本人两张底牌；指针/触控松开、
取消、移出，键盘 Enter/Space 松开，窗口失焦、页面隐藏、离线、离房、连接接管或权威
手牌变化时必须立即遮盖。按钮必须支持键盘按住语义，不能通过单击切换为持续可见。
玩家完成开手确认后即可在等待其他人期间使用该按钮；本人弃牌后在本手仍活动时仍可查看
自己的牌，进入完整结算后按既有受控摊牌摘要规则处理。

### 5.6 德州扑克下注缓存与筹码列表

**FR-024** 下注缓存不得再位于底部操作区域内。只有轮到本人正式行动时，牌桌上才显示
一张半透明悬浮缓存卡；其他玩家回合、开手确认、自动推进、摊牌和完整结算时必须隐藏。
缓存不得遮挡公共牌、底池、开手卡、底牌查看层或必要玩家状态。

**FR-025** 缓存卡在本人回合内从空到加入筹码必须保持稳定高度和受限宽度，不得因加入
第一枚或更多筹码发生明显高度突变。可见布局必须：

- 移除“下注缓存”四个可见文字，但保留可访问名称；
- 左侧直接从第一枚筹码开始，第一枚筹码左边缘完整可见；
- 右侧集中显示当前缓存总额和“清空”；
- 最左和最右筹码始终完整位于卡片边界内；
- 内容未达宽度上限时使用正常间距，达到上限后按可用宽度自动、等距地增加中间筹码
  重叠，不能裁剪端点；
- 相同面值合并为一枚筹码与 `×数量` 时，面值和数量的上下间隔必须更紧凑且仍可读。

**FR-026** 下注缓存和筹码面值列表不得再注册 HTML 拖放、指针拖入/拖回或吞掉横向手势。
点击、轻触和键盘激活面值继续向缓存增加一枚；激活缓存筹码继续移除一枚；清空、跟注
填充、全押填充和权威确认语义保持。手机在筹码列表上横向滑动必须优先正常滚动列表，
不得生成下注拖动输入或页面横向溢出。

**FR-027** 缓存仍是本机未确认草稿：行动者、当前下注、最小加注、筹码余额、阶段、
Poker 版本或房间权威变化使它过期时必须清空；刷新、重连、接管和重启不得把缓存变成
权威下注。固定面值、合法跟注/加注/全押、禁用原因和确认命令继续由既有规则决定。

### 5.7 德州扑克手机牌桌

**FR-028** 手机横向玩家卡列表必须为阴影和庄家标识保留上下溢出空间；滚动容器不得
裁剪卡片阴影、焦点轮廓或位于卡片外沿的庄家标识。横向滚动、滚动吸附、长按房主管理
和 300px 宽度必须同时可用。

**FR-029** 手机公共牌必须在每张牌边界内完整显示点数和花色，不得溢出或互相覆盖。
移除常态底牌后，公共牌区域应使用释放出的中心空间，在 300px 与常见手机宽度中尽可能
放大五张公共牌，同时不覆盖底池、玩家卡、开手卡或下注缓存，并降低旁观者从常态界面
窥见本人底牌的机会。

## 6. 用户流程或调用流程

### 6.1 共用顶栏

1. 已登录用户进入任一 Poker/Avalon 房间。
2. 左侧可以返回大厅或按合法语义确认离房；中间查看房间名、游戏名和当前阶段。
3. 只有房主在右侧看到关闭房间；房间内没有公共大屏入口。
4. 用户返回大厅后，从对应房间卡打开匿名公共大屏。

### 6.2 阿瓦隆准备和角色构成

1. 房主和非房主看到相同准备卡；非房主准备/取消，房主按既有资格开始。
2. 准备人数变化时，十个圆点和标题下角色构成实时更新；不足五人显示最低人数提示。
3. 房主在准备卡下方编辑独立设置卡；保存后准备集合按既有规则清空并重新计算构成。
4. 玩家点击房间名区域查看同一构成浮层；匿名大屏在“本局参赛”上方持续显示构成卡。
5. 开局后构成冻结为本局参与人数和配置，但具体角色归属继续按既有秘密规则投影。

### 6.3 Poker 开手

1. 房主从等待或完整结算显式开始一手，服务端冻结参与者、位置、面值、庄家和盲注；
   筹码＋牌模式同时安全洗牌、发牌，但不自动扣盲注。
2. 非盲注玩家立即完成线上底牌或实体底牌确认；大小盲先按固定按钮提交盲注，再确认。
3. 所有客户端可以并行完成自己的动作，公开玩家卡只显示谁仍待完成，不显示任何牌面。
4. 全部仍有效参与者完成后，服务端进入翻牌前并设置第一行动者。
5. 有人断线则等待；重连继续，或由房主移除/关闭按现有资产语义安全收口。

### 6.4 正式行动与查看底牌

1. 当前行动者整卡填充操作提示色；本人卡同时保留独立边框。
2. 筹码面值列表支持点击、触控和键盘，横向滑动只滚动列表。
3. 只有当前行动者看到牌桌悬浮下注缓存，并通过底部动作按钮确认权威下注。
4. 本人需要查看线上底牌时按住“查看底牌”，松开或发生安全事件后立即遮盖。
5. 牌桌常态只保留公共牌和底池，不把本人底牌留在共享视野中。

## 7. 数据、接口与状态

1. `PokerState` 必须持久表达开手确认阶段、每个指定盲注是否已提交、每个参与者是否已
   完成底牌/实体牌确认，以及版本。可以复用现有 `blinds` 阶段；具体字段名由规划与设计
   决定，但状态必须能无歧义地区分 FR-012 的所有公开状态。
2. 筹码＋牌模式可以在开手确认阶段持久保存已发底牌；纯筹码模式不得创建线上牌。
3. 新的盲注与确认写操作必须使用现有命令信封、命令 ID、控制租约、期望 Poker 版本、
   Zod 校验、事务和 `processed_commands` 幂等结果。只有指定参与者可以提交自己的动作，
   只有指定小盲/大盲可以提交对应固定盲注。
4. 公开 Poker 投影必须提供显示开手阶段和未完成人员所需的非秘密状态。本人私有投影
   继续只向有效租约下的当前参与者提供本人底牌；任何公开字段不得推导出牌面。
5. Avalon 角色构成由公开房间配置与当前选中或冻结参与人数派生，不新增具体角色归属
   投影。匿名大屏只消费同一公开构成。
6. 下注缓存、角色构成浮层是否打开、底牌是否正在按住显示属于本机瞬时 UI 状态，不写
   SQLite、命令或 WebSocket。
7. `room.pause`、`room.resume` 和 `avalon.void` 不再属于当前 Web 支持的用户流程；服务
   可以移除或确定性拒绝这些外部命令，但关闭/离开/移除等内部安全作废路径不得依赖用户
   重新获得手动作废入口。
8. 旧活动 Poker 快照若没有新的开手字段，必须解释为其既有盲注和开手步骤已经完成，
   不得重新发牌、重新扣盲注或要求全员再次确认。旧 `paused` 房间不得被静默推进或改写
   资产；当前产品无需提供恢复入口，但房主必须仍能安全关闭该房间。
9. 现有版本化 JSON 快照足以承载新增状态时无需新增 SQL 表；任何兼容归一化必须原子、
   可重复且不改变已确认资产。数据回滚继续依赖受支持部署流程中的完整 SQLite 备份。

## 8. 异常、边界与恢复

1. 非指定盲注者、错误盲位、错误模式、重复盲注、重复确认、确认顺序错误、过期版本、
   失效租约或跨房命令必须无状态变化拒绝。
2. 盲注事务失败不得留下“筹码已扣但状态未确认”或“状态确认但流水未记录”的部分结果；
   成功重试不得重复扣款。
3. 大小盲可以任意顺序提交；正式开局前 `actingAccountId` 不得让普通下注命令生效。
4. 短额小盲/大盲按剩余筹码全押，正式翻牌前仍遵守既有完整大盲开局跟注额、行动跳过
   全押者、边池和守恒规则。
5. 开手阶段玩家断线不自动操作；重新连接、刷新、控制接管和服务重启必须恢复相同牌、
   相同盲注、相同确认集合和相同待办。
6. 房主移除开手阶段玩家时，已投入盲注留池、剩余筹码兑换、玩家弃牌；如果人数或资格
   变化使手牌不能继续，必须走既有安全结算或作废路径，不得悬挂状态。
7. 房主关闭、房主无继任者退出、活动 Avalon 参赛者离开/移除等自动安全路径仍可以
   内部作废并退款；这不构成被取消的“手动作废功能”。
8. 新客户端不得新建 paused 状态。旧 paused 快照保持已确认状态且只能安全关闭，不得
   因移除恢复入口而破坏资产、秘密或数据库加载。
9. 查看底牌层和 Avalon 构成浮层在所有指定安全事件后必须关闭；浏览器视觉残影或本机
   状态不得把秘密保留到另一个账户、连接或房间。
10. 自定义 Avalon 角色数与当前选中人数不兼容时必须明确提示；服务端仍最终拒绝非法
    开局且不托管押分。
11. 筹码缓存达到最大 16 种面值、使用长数字或 300px 视口时必须保持端点完整、总额与
    清空可达；横向滑动不得误加或误删筹码。
12. 固定顶栏、悬浮开手卡、底牌层、下注缓存、结算层和 portal 菜单的层级必须避免互相
    遮断唯一合法操作；窗口过小时使用受控滚动而不是页面横向溢出。

## 9. 非功能需求

**NFR-001 服务端权威与并发**：盲注、确认、阶段推进、行动者、关闭和自动安全作废必须
版本化、幂等、原子且由服务端授权；客户端计数和动画不能决定游戏状态。

**NFR-002 资产完整性**：账户分数、牌桌筹码、下注和底池继续使用安全整数及原子流水，
总量守恒；游戏资产与转移金额不得为负，失败不得部分提交。

**NFR-003 隐私**：活动 Poker 私牌只进入本人有效控制租约投影；活动 Avalon 的具体
角色、知识和秘密动作继续按既有边界隔离。角色构成公开不得包含角色归属。匿名大屏始终
只读且不占名额。

**NFR-004 恢复与兼容**：旧 SQLite 快照、既有活动手牌、房间、结果、流水、账户、赛季、
排行榜、公共大屏和 `/data` 卷必须安全加载；升级不得重发牌、重扣盲注、重放命令或改变
已确认资产。

**NFR-005 响应式与可访问性**：桌面和 300px 动态视口不得页面横溢；键盘、触控和鼠标
均能完成全流程。图标按钮、按住查看、浮层、状态色、双列玩家卡和横向筹码滚动必须具有
可读名称、焦点、非颜色语义和 `prefers-reduced-motion` 兼容。

**NFR-006 本地化**：全部新增阶段、盲位提示、实体牌确认、角色构成、人数不匹配、按钮、
错误和可访问名称必须提供语义一致的简体中文和英文。

**NFR-007 性能与容量**：约 15 个在线账户、1–2 个房间、十名玩家、多匿名大屏及最多
16 种筹码面值下不得出现无界 DOM、跨房状态、持续卡顿或高频整桌重绘。自适应筹码重叠
不得复制实际筹码数量级的 DOM。

**NFR-008 离线运行**：不得新增公网、CDN、云数据库、第三方身份、远程字体或实时依赖；
构建后静态资源必须完全本地。

**NFR-009 工程边界**：保持严格 TypeScript、ESM、React 19 和现有 workspace 分层。
共享契约变化必须同步领域、Poker 引擎、服务投影、Web 类型使用和相关测试。

**NFR-010 可观察性**：日志可以记录非敏感命令类型、版本、拒绝原因和恢复结果，但不得
记录私牌、Avalon 角色归属/知识、令牌或真实部署配置。

**NFR-011 构建与发布**：生产构建继续适用于 `linux/amd64` iStoreOS 非 root 容器和
既有健康接口。正式服务器部署不属于本功能验收，仍需独立明确授权。

7. 主要影响文件预计包括：
   `apps/web/src/main.tsx`、`apps/web/src/avalon-ui.tsx`、
   `apps/web/src/styles.css`、`apps/web/src/locales.ts`、

8. 主要风险是盲注流水重复、旧手牌被误判为待确认、断线形成永久阻塞、私牌在 UI 层残留、
   外部旧暂停命令兼容、多个悬浮层互相遮挡及 300px 几何回归。后续规划必须为这些风险
   指定最小充分的权威状态、兼容和浏览器证据，但本需求阶段不分解执行阶段。
