# 阿瓦隆游戏：需求

- 功能标识：`avalon-game`
- 文档状态：已澄清、可进入独立规划
- schema：`3.2`
- 需求确认日期：`2026-07-31`
- 项目基线：`main` / `67e68cea036a41c38917e19936c27e3f7cd49f19`

## 1. 背景与目标

当前家庭聚会游戏平台已经提供可信家庭局域网内的免密码账户、房间、赛季、排行榜、
守恒型积分、实时同步、公共大屏、SQLite 恢复和完整德州扑克。平台原始定位明确预留了
阿瓦隆等后续游戏，但现有共享 `Room`、房间配置、服务命令和主要游戏 UI 仍以
`texas-holdem` 为唯一游戏类型。

本功能新增完整可玩的原版《The Resistance: Avalon》阿瓦隆，支持 5–10 名实际参赛者、
服务器随机角色、房间角色预设与自定义配置、自动认角色和实体桌游式手动认角色两种模式，
并把组队、全员投票、任务成功/失败选择、任务判定、连续否决、刺客刺杀和最终结算全部放在
网站中完成。

玩家界面沿用德州扑克的产品语言和响应式结构：上方展示参与者，中间展示当前任务、组队、
投票、成功/失败轨迹、人数和规则阈值，下方展示当前玩家可执行的上下文操作。自动模式允许
玩家查看本人角色及原规则允许知道的玩家关系，并提供即时防窥遮盖；手动模式只通过网站
显示本人角色，其他认人信息通过开局“天黑请闭眼”的实体流程获得。

阿瓦隆胜负接入现有赛季积分与排行榜。每局使用守恒押分：败方损失押分，胜方分配败方押分，
全局总量不因对局改变。用户同时明确要求把平台账户积分从当前“非负且禁止透支”改为没有
业务上限或下限的有符号安全整数；阿瓦隆和德州扑克均可使账户积分变为负数，但扑克桌上
筹码、下注、底池、买入值和补码值仍不得为负。

## 2. 范围

### 2.1 包含范围

- 在大厅创建、发现、加入、返回和关闭阿瓦隆房间，并与德州扑克房间明确区分。
- 5–10 人原版善恶人数、五项固定顺序任务、队伍人数、第四任务双失败阈值、五次连续否决、
  三次任务成败及刺客刺杀规则。
- 原版角色：梅林、派西维尔、亚瑟忠臣、刺客、莫甘娜、莫德雷德、奥伯伦和普通邪恶爪牙。
- 管理员为 5、6、7、8、9、10 人分别维护唯一一套阿瓦隆角色预设；房主可选择该预设或
  合法自定义角色配置。
- 开房时可选择奥伯伦原版可见性或当前 Dized 可见性，默认使用原版。
- 自动认角色模式、手动“天黑请闭眼”认角色模式、角色查看确认和本机防窥遮盖。
- 首局前和局间统一准备；房主明确开始；未准备成员和局中加入成员以公开观战身份等待下一局。
- 网站内完成队长选人、秘密投票后公开个人票、秘密任务选择后只公开汇总、刺客选择和结算。
- 匿名只读公共大屏显示全部公开局势，并在手动模式承担夜间文字步骤展示。
- 每局正整数押分托管、胜负分配、作废退款、每人有符号积分变化和赛季参赛事实。
- 全平台账户分数、赛季基础分、排行榜、历史快照、资产流水、账户退役和德州扑克余额检查
  迁移为有符号安全整数语义。
- SQLite 持久化、幂等命令、版本并发、刷新、重连、控制接管、服务重启和旧快照兼容。
- 简体中文与英文、账户亮暗主题、账户音量、桌面、300px 窄屏、键盘、鼠标和触控。

### 2.2 不包含范围

- 不包含湖中仙女、兰斯洛特、任务目标选择/乱序、剧情卡、忠诚卡、Excalibur 或其他扩展
  模块；原因是用户要求 initial 先完成原版，扩展留待后续独立需求。
- 不提供机器人、在线匹配、内置语音聊天、文字聊天、讨论计时器或自动替玩家投票。
- 不提供录制夜间语音、浏览器语音合成或远程音频；手动模式首版使用本地化文字步骤。
- 不提供房主指定具体玩家角色、查看完整角色映射、代替其他玩家投票/执行任务或代替刺客选择。
- 不提供可命名保存的个人角色预设库；管理员每人数唯一预设和房间自定义已覆盖 initial 范围。
- 不新增永久对局回放或跨赛季阿瓦隆历史浏览页面；只持久化恢复、排行榜、当前结算和审计所需
  结果。
- 不改变可信 LAN、无密码、匿名 `/admin` 的既有信任模型，也不把产品直接暴露到公网。
- 不在本需求阶段执行正式 iStoreOS 发布；正式部署仍需独立明确授权并使用现有受支持入口。

## 3. 已确认的项目事实与约束

- 当前 `Room.gameType`、`RoomConfig`、`RoomProjection`、大厅房间摘要、`room.create`、
  `room.join`、`room.start` 和 Web 游戏分支均以德州扑克为唯一形态；新增阿瓦隆需要
  共享契约、平台领域、服务分发、投影和 Web 的显式游戏判别，不能只增加前端页面。
- 当前 `PlatformParticipationFact.gameType` 已是字符串，排行榜只消费有效、未撤销结果的
  参与账户，不读取扑克牌型或下注；这是阿瓦隆结果接入游戏无关排行榜的现有边界。
- 当前平台明确把账户分数限制为非负整数，买入和补码会检查余额，领域不变量会拒绝负资产。
  本需求经用户明确确认替换该行为为有符号安全整数账户分数，并同时调整德州扑克余额检查；
  冻结历史工作流文档不回写，后续实现证据必须把此项记录为本功能的跨平台兼容变化。
- 当前德州扑克的筹码、下注、底池、盲注、买入和补码金额均为正数或非负数。负账户分数
  不得扩散为负桌上筹码、负下注、负底池或绕过房间买入上下限。
- 一个账户当前只能占用一个受管房间；房间具有房主、在线状态、准备集合、控制租约、
  版本、命令 ID、暂停/恢复、超时转让和安全关闭语义。阿瓦隆必须复用这些平台不变量。
- 当前命名成员上限为 10，匿名 display 不占名额且可多开。阿瓦隆原版也是 5–10 人，
  因此保留 10 个带身份房间成员上限，不引入第二套容量规则。
- 当前公共大屏匿名、只读、不占成员名额；隐藏牌只进入本人有效控制租约投影。阿瓦隆角色、
  未公开投票和任务选择必须沿用同等级、按角色更细化的服务端投影隔离。
- 当前 SQLite 持久化主体是版本化平台 JSON 快照与幂等命令结果。旧数据不包含阿瓦隆状态，
  且所有现有分数均非负；升级必须把旧数据视为合法有符号值，不得重写现有账户、赛季、
  房间、手牌、流水或历史快照。
- 当前账户语言、`light`/`dark` 主题和 `0–100` 音量由服务器持久化；所有新固定文案必须
  双语，音效失败不得阻塞业务。阿瓦隆不得重新引入设备级玩家偏好权威。
- 项目级 `docs/ui-design-guidelines.md` 要求固定外框、唯一内部滚动区、稳定滚动槽、
  portal 弹层、300px 无横向溢出、键盘/触控和 `focus-visible`。阿瓦隆角色层、确认层、
  自定义角色编辑和玩家操作区必须遵守该规范。
- 原版人数与阵营为：5 人 3 善/2 恶；6 人 4 善/2 恶；7 人 4 善/3 恶；8 人 5 善/3 恶；
  9 人 6 善/3 恶；10 人 6 善/4 恶。
- 五项任务人数依次为：5 人 `2/3/2/3/3`，6 人 `2/3/4/3/4`，7 人 `2/3/3/4/4`，
  8–10 人 `3/4/4/5/5`。7 人及以上只有第四项任务需要至少两张失败牌才失败，其余任务
  至少一张失败即失败。
- 原版纸质规则与当前 Dized 对奥伯伦是否被梅林看见存在差异。用户要求兼容两种房间规则，
  以原版“梅林看见奥伯伦”为默认。
- 规则资料基线为[原版规则书 PDF 镜像](https://cdn.1j1ju.com/medias/a6/dc/c1-the-resistance-avalon-rulebook.pdf)
  与出版方验证维护的 [Dized 当前规则](https://rules.dized.com/game/rZluqS52QmGdpoVxcmVLtg/the-resistance-avalon)；
  奥伯伦差异另见 [Dized 奥伯伦规则](https://rules.dized.com/game/rZluqS52QmGdpoVxcmVLtg/kyuq11xwSK64FHOLrK_SQw/oberon)。
  实现以本需求显式规则和每局冻结设置为权威，外部资料后续变化不得静默改变既有房间或对局。
- 澄清开始及需求写入前工作区均为干净的 `main`，基线提交为
  `67e68cea036a41c38917e19936c27e3f7cd49f19`。既有功能工作流均已冻结，本功能使用独立
  schema-v3.2 目录，不修改既有 initial/change 历史。

## 4. 交付与验证策略

- 本次 `initial` 运行采用用户明确选择的 `relaxed` 策略。
- 实现可以先于测试，但全部 `core` 验收、项目硬门禁、角色隐私、投票/任务隐私、积分守恒、
  有符号算术安全、扑克兼容、构建、恢复和离线运行始终阻塞完成。
- 只有经独立证据证明不影响交付行为的 `supplemental` 异常，才可保留为带严重程度的
  `FND-I-*` report-only 发现项；不得在失败后把 core 项降级。
- 角色投影、全平台积分语义和旧 SQLite 恢复属于高风险跨层变化。后续规划必须提供与风险
  相称的原子性、隐私、兼容和恢复验证，但不得仅按前端、后端、测试或文档机械拆阶段。

## 5. 功能需求

### 5.1 平台游戏边界与有符号积分

**FR-001** 平台房间必须使用显式游戏类型区分至少 `texas-holdem` 与 `avalon`。大厅、
服务端命令、房间投影、Web 游戏路由和持久化恢复必须按游戏类型选择合法配置和状态；
阿瓦隆命令不得被发送到扑克房间，扑克命令也不得作用于阿瓦隆房间。

**FR-002** 大厅创建房间必须先选择游戏。扑克创建流程保留既有模式、盲注、买入和面值语义；
阿瓦隆创建流程使用阿瓦隆模式、角色方案、奥伯伦规则和每局押分，不要求加入时买入筹码。
房间卡片必须显示游戏名称、状态、人数和与该游戏相关的简明配置，不把扑克盲注字段套用于
阿瓦隆。

**FR-003** 账户当前赛季分数、赛季基础分和排行榜分数必须改为无产品业务上限/下限的
有符号整数。所有输入、存储和运算结果仍必须是 JavaScript 安全整数；任何一步可能越过
安全整数范围时，完整命令必须在写入前拒绝。

**FR-004** 德州扑克买入和补码仍必须是正安全整数并遵守房间最小/最大买入、补码时点、
桌上筹码上限和现有牌局规则，但不得再因账户当前分数低于买入或补码金额而拒绝。转移可使
账户分数为负；扑克桌上筹码、当前下注、总下注和底池始终不得为负。

**FR-005** 阿瓦隆押分、德州扑克买入/下注/结算、账户分数、游戏托管资产和资产流水必须
形成统一的有符号守恒模型。除新账户/新赛季基础分发行和明确的账户退役外，任何游戏命令
前后所有账户分数与受管游戏资产的有符号总和必须完全相等。

**FR-006** 账户删除必须正确处理正、零或负分账户。退役记录必须以方向明确且金额非负的
成组流水表达正资产或负债退出，使“发行、退役、活动账户和游戏内资产”的有符号守恒关系
可验证；不得用负流水金额、静默归零或删除审计记录掩盖差额。

**FR-007** 当前及历史排行榜必须正确排序和显示有符号分数，包括负号和零。加入任一游戏
房间后的冻结排行榜、离开/关闭后的更新、历史赛季快照、删除匿名化和同名重建隔离语义
保持不变。

**FR-008** 旧 SQLite 快照中的现有非负分数必须原值加载为合法有符号分数，不要求数据
重算。新版本写入的负分若回退到不支持负分的旧镜像，必须使用升级前完整 SQLite 备份，
不得让旧代码直接解释新状态。

**FR-009** 重复、过期、并发、跨游戏、持久化失败或安全整数溢出的积分命令不得产生负
游戏资产、重复托管、重复派分、部分流水或部分状态。服务端领域与事务边界而非客户端按钮
负责执行这些规则。

### 5.2 阿瓦隆设置、角色配置与房间准备

**FR-010** `GlobalSettings` 必须新增阿瓦隆设置分组，至少包含默认模式、默认奥伯伦规则、
默认每局押分以及 5–10 人各一套角色预设。新安装默认自动模式、原版奥伯伦规则和押分
`100`；管理员必须通过现有原子全局保存一次提交通用、扑克和阿瓦隆设置，任一无效字段使
全部设置无变化失败。

**FR-011** 每人数唯一管理员预设的初始构成为：

- 5 人：梅林、派西维尔、1 名亚瑟忠臣；刺客、莫甘娜。
- 6 人：梅林、派西维尔、2 名亚瑟忠臣；刺客、莫甘娜。
- 7 人：梅林、派西维尔、2 名亚瑟忠臣；刺客、莫甘娜、莫德雷德。
- 8 人：梅林、派西维尔、3 名亚瑟忠臣；刺客、莫甘娜、莫德雷德。
- 9 人：梅林、派西维尔、4 名亚瑟忠臣；刺客、莫甘娜、莫德雷德。
- 10 人：梅林、派西维尔、4 名亚瑟忠臣；刺客、莫甘娜、莫德雷德、奥伯伦。

管理员可独立修改每个人数的预设。管理员修改只初始化后续新房间或房主明确重新采用的预设，
不得暗改已经创建的房间配置或活动对局快照。

**FR-012** 房主可在创建房间和每局准备阶段选择该人数的管理员预设或自定义角色。自定义
必须满足原版善恶人数、梅林和刺客各一且必选、每个特殊角色最多一名、剩余空位由普通忠臣
或普通邪恶补齐；5 人包含派西维尔时必须同时包含莫甘娜或莫德雷德。无效、人数不匹配或
重复角色配置必须由客户端提示并由服务端原子拒绝。

**FR-013** 房间可选择 `original` 或 `dized` 奥伯伦可见性并默认 `original`：

- 两种规则下，奥伯伦均属于邪恶，但不知道其他邪恶，其他邪恶也不知道奥伯伦。
- `original` 下梅林看见奥伯伦为邪恶；`dized` 下奥伯伦也对梅林隐藏。
- 该设置只在配置包含奥伯伦时改变认人投影和夜间步骤，不改变奥伯伦的投票、任务和胜负阵营。

**FR-014** 房主可在准备阶段修改自动/手动模式、预设/自定义角色、奥伯伦规则和押分。
每局开始必须原子冻结实际参赛者、座位顺序、角色列表、模式、奥伯伦规则、押分、任务表和
起始队长；管理员或房主之后的设置变化只作用于下一局。

**FR-015** 首局前和每局完整结算后必须使用统一准备协议：房主自动准备并必定参赛；其他
成员可准备或取消。只有 5–10 名在线准备者时房主才可明确开始，系统不得自动开局；账户
分数无论正负均不影响准备资格。若存在未准备成员，房主开始前必须确认他们本局只观战。

**FR-016** 等待、进行中、暂停和结算阶段均允许在未满 10 个带身份成员时加入。活动对局
加入者不得插入当前角色集合、队长顺序、投票或任务，只能获得公共观战投影；当前局结束后
进入准备阶段。匿名大屏继续不计成员名额且可多开。

**FR-017** 房主转让、断线超时、暂停、恢复和关闭房间继续使用平台权威语义。房间房主与
阿瓦隆当前队长是两个独立角色：转让房主不得改变已冻结的队长顺序，轮转队长也不得改变
房间管理权限。

**FR-018** 活动阿瓦隆参赛者不得正常退出后让对局继续。参赛者确认退出、被房主移除、
被管理员删除或房主选择作废当前局时，服务端必须作废整局、完整退回全部押分、保存必要的
作废审计但不产生排行榜参赛事实，并让仍在房间的成员回到局间准备；随后再执行成员移除、
房主转让或账户退役。

**FR-019** 完整结算后不得自动开始下一局。角色、最终积分变化和胜因保持显示，成员可退出、
加入、修改下一局配置并重新准备；下一局重新随机角色和起始队长，不沿用上一局私有知识。

### 5.3 角色分配、自动模式、手动模式与隐私

**FR-020** 每局角色必须由服务端使用不可由客户端或房主操控的随机顺序分配给冻结参赛者。
房主、管理员投影、其他玩家、观众和活动期公共大屏不得取得完整映射。每名有效控制租约的
参赛者只可取得自己的精确角色和当前模式允许的知识。

**FR-021** 自动模式必须按规则关系展示而不是泄露其他人的精确特殊角色：

- 梅林看到除莫德雷德外的邪恶玩家；奥伯伦是否可见由 FR-013 决定，但名单不标注具体角色。
- 派西维尔看到梅林与莫甘娜候选；有莫甘娜时两者必须不可区分，没有莫甘娜时只看到梅林。
- 除奥伯伦外的邪恶玩家相互识别为邪恶同伴，但不得看到同伴的精确特殊角色，也不得看到
  奥伯伦。
- 奥伯伦、普通亚瑟忠臣及没有额外知识的角色不获得额外名单。

**FR-022** 手动模式的私人投影必须只显示本人精确角色和角色说明，不得显示梅林所见邪恶、
派西维尔候选或邪恶同伴名单。服务器仍保存角色映射并执行合法动作与最终胜负，实体认人
遗漏或玩家未按夜间步骤行动不得使服务器泄露额外名单作为补偿。

**FR-023** 手动模式必须根据实际角色组合和奥伯伦规则生成完整中英文夜间文字步骤，覆盖
全员闭眼、邪恶互认、梅林认邪恶、派西维尔认候选和全员睁眼；不存在的角色步骤不得误导性
出现。房主端和公共大屏均可展示，房主逐步推进，并且只允许在第一次队伍提名前重新开始
整套夜间流程。首版不得依赖录制语音、浏览器语音合成或公网资源。

**FR-024** 私密角色区必须默认遮盖。玩家明确操作后才显示本人角色和自动模式知识，并可
一键立即隐藏；浏览器进入后台、刷新、重连、控制权被其他设备接管或离开房间时必须自动
重新遮盖。遮盖状态只属于当前设备显示，不写入服务器，也不得删除玩家仍依法可重新查看的
私有知识。

**FR-025** 自动模式在全部参赛者确认已查看本人角色后进入第一次队伍提名；手动模式在全部
参赛者确认已查看本人角色且房主完成夜间步骤后进入。确认只表示流程就绪，不公开角色或
知识，也不能由房主代确认。断线玩家不得被视为已完成新的确认。

**FR-026** 进行中角色、自动模式知识、未公开投票、任务选择和刺客未提交目标不得进入
大厅、公共房间、观众、公共大屏、其他玩家、管理员最小投影或普通日志。服务端必须提供
等价于现有私牌泄漏断言的阿瓦隆私有状态检查。

**FR-027** 刷新、短暂断网、控制接管和服务重启不得重新分配角色、改变知识关系或提前
公开秘密。有效租约恢复后本人可重新取得相同私有投影；旧租约立即失效且不得继续收到
角色或待选操作。

**FR-028** 只有对局进入最终完整结算后，全部角色和阵营才可作为公开结果显示给玩家、
观众和公共大屏。作废对局不得因作废本身自动公开角色；服务器仅保留受控恢复/审计数据。

### 5.4 原版对局状态机

**FR-029** 每局必须按 FR-030 中确认的 5–10 人善恶数量建立阵营。梅林和刺客始终存在；
三次任务成功只是进入刺杀阶段，不在刺客选择完成前确定善方最终胜利。

**FR-030** 五项任务必须按固定顺序使用以下队伍人数和失败阈值：

| 参赛人数 | 善方/邪恶 | 任务人数 1–5 | 第四任务失败阈值 |
| --- | --- | --- | --- |
| 5 | 3 / 2 | 2 / 3 / 2 / 3 / 3 | 1 |
| 6 | 4 / 2 | 2 / 3 / 4 / 3 / 4 | 1 |
| 7 | 4 / 3 | 2 / 3 / 3 / 4 / 4 | 2 |
| 8 | 5 / 3 | 3 / 4 / 4 / 5 / 5 | 2 |
| 9 | 6 / 3 | 3 / 4 / 4 / 5 / 5 | 2 |
| 10 | 6 / 4 | 3 / 4 / 4 / 5 / 5 | 2 |

除表中 7 人以上第四任务外，任一任务出现至少一张失败即失败。

**FR-031** 第一任队长必须从冻结参赛者中服务端随机选择。每次队伍被否决或任务完成后，
队长按冻结座位顺序移交给下一名参赛者并循环；暂停、房主转让、刷新或观战加入不得改变
顺序。

**FR-032** 当前队长可在任意讨论时间后选择恰好等于当前任务要求的人数，允许选择自己，
同一人不得重复。提交前可调整；提交后队伍冻结并进入全员投票，非队长和房间房主不得代替
当前队长提交。

**FR-033** 每名参赛者包括当前队长都必须秘密提交赞成或反对，提交后不可撤销或修改。
提交进度可公开，但具体票在全员提交前不得公开。全员提交后同时公开每名玩家的票；赞成
严格超过半数才通过，平票视为否决。

**FR-034** 同一项任务内每次否决使连续否决计数加一并轮转队长。第五次连续否决后立即由
邪恶阵营获胜，不再允许第五名之后的额外强制队伍；任务完成后下一项任务的否决计数重置。

**FR-035** 队伍通过后，只有入选任务队员可以秘密提交任务选择。善方角色只能提交成功；
邪恶角色可以提交成功或失败。客户端不得向善方渲染可用的失败操作，服务端仍必须拒绝
构造的善方失败命令。

**FR-036** 任务选择提交后不可撤销或修改。提交进度可公开，但全员提交前不得公开选项；
完成后只公开成功张数、失败张数和任务成功/失败，不得公开每张选择与玩家的对应关系，
也不得通过顺序、动画、响应时间或日志建立该映射。

**FR-037** 任务结果按 FR-030 阈值判定并记录到五项轨迹。未达到任一阵营终局条件时，
进入下一项任务、重置否决计数并沿座位顺序轮转队长。

**FR-038** 第三项失败任务出现后，邪恶阵营立即最终获胜；不得进入额外投票、任务或刺杀。
第三项成功任务出现后必须进入刺杀阶段，不得先结算善方积分。

**FR-039** 刺杀阶段允许邪恶阵营线下讨论，但只有刺客本人有效租约可提交一次目标。候选
界面不得通过只列善方、禁用邪恶或标注阵营泄露未知角色，应允许从除刺客本人外的冻结参赛者
中选择；服务端只以目标是否为梅林判定。

**FR-040** 刺客命中梅林时邪恶最终获胜；未命中时善方最终获胜。提交后不可撤销，必须
立即进入完整结算并公开最终角色、胜因和积分变化。

**FR-041** 需要某名玩家操作而其断线时必须无限等待，不得自动赞成、反对、成功、失败或
代选刺杀目标。房主可暂停、恢复或作废；产品不引入讨论/行动倒计时。

**FR-042** 队伍提交、投票、任务选择、任务判定、队长轮转、五次否决和刺杀必须受命令 ID、
期望平台版本、期望阿瓦隆版本及 SQLite 单事务约束。并发提交只能产生一个权威结果，
过期或重复请求不得推进两次。

**FR-043** 当前对局必须保存并展示全部已公开的队伍提名、个人投票、任务成功/失败汇总、
队长顺序和胜负轨迹，供现场推理；不得保存或展示任务选择的玩家对应关系。initial 不要求
跨房间历史回放界面。

### 5.5 押分、结算、排行榜与作废

**FR-044** 阿瓦隆每局押分必须是安全整数且至少为 `2`。最小值 `2` 用于保证所有合法人数
和任一胜方阵营下，每名胜方成员都能获得至少 1 分正净收益。账户余额不构成准备或开局
门禁；开局时从每名冻结参赛者账户向该局托管区转移同额押分，允许账户因此变为负数。

**FR-045** 最终结算必须先把每名胜方自己的押分原额返还，再把全部败方押分按胜方人数
整除分配。每名胜方先得到商，余数按冻结座位顺序从最前胜方开始每人加 1；每名败方净变化
为负一个押分，每名胜方净变化为正，所有净变化精确求和为零。

**FR-046** 最终胜方必须以完整规则结果决定：三次任务失败或五次连续否决为邪恶胜；三次
任务成功后刺客命中梅林仍为邪恶胜，否则为善方胜。不得在刺杀前按任务成功临时派分。

**FR-047** 玩家退出/移除、管理员删除、房主作废、房间安全关闭、配置/状态无法继续或
持久化事务失败导致对局作废时，所有已托管押分必须原路全额返还或在同一账户即将删除时
纳入其有符号退役处理；作废局净游戏变化为零且不进入有效排行榜参赛事实。

**FR-048** 正常结算必须持久保存游戏类型、赛季、房间、局号、冻结参与者、角色与阵营、
公开流程摘要、胜方、胜因、每人有符号积分变化、结算后账户分数和时间。当前及未来排行榜
把所有实际参赛者计入资格，包括零以外的任意正负最终分数；观众、未准备成员和作废局不计。

**FR-049** 押分托管、终局判定、派分、结果记录、排行榜参赛事实和房间完整结算状态必须
在同一原子命令中全成或全败。守恒、安全整数或持久化失败必须使所有账户、托管、结果和
游戏阶段保持提交前状态。

### 5.6 玩家界面、公共大屏与本地化

**FR-050** 阿瓦隆玩家页面必须沿用德州扑克的整体交互语言和三段牌桌布局，但使用阿瓦隆
语义内容：上方参与者、中间公共局势、下方当前操作。布局不得把扑克盲注、筹码堆、公共牌
或底池当作阿瓦隆状态。

**FR-051** 上方参与者区域必须按冻结/房间座位稳定展示头像、用户名、在线状态、当前队长、
已选任务队员、已提交公开阶段状态和本人标记。进行中不得显示角色或阵营；观战成员必须
与实际参赛者明确区分。

**FR-052** 中间区域必须同时显示五项任务轨迹、当前任务序号、要求人数、失败阈值、善恶
任务成功数、当前连续否决数、当前队长、已提交队伍、投票/任务提交进度和全部已公开历史。
关键信息不得只靠颜色、图标或动画表达。

**FR-053** 下方操作区必须只显示当前玩家此刻合法且相关的操作：查看/隐藏角色、确认角色、
房主夜间步骤、队长选人、投票、任务成功/失败、刺客选择、准备/取消、房主开始、暂停/恢复、
作废、退出或只读等待。服务端拒绝仍是最终权限边界。

**FR-054** 自动/手动模式、奥伯伦规则、当前角色、规则知识、队伍人数、失败阈值、投票
结果、任务结果、胜因、积分变化和所有错误必须提供简体中文与英文。角色说明必须简洁准确，
不得通过翻译把“候选关系”误写成确定角色。

**FR-055** 公共大屏必须匿名、只读、不占名额，并显示参与者、当前队长、公开队伍、公开后
个人投票、任务成功/失败汇总、任务轨迹、否决计数、待提交人数和公开结算。它不得显示活动
角色、自动知识、未公开票、任务选择、刺客未提交目标或任何操作按钮。

**FR-056** 手动模式公共大屏可在认人阶段显示 FR-023 的通用夜间文字步骤；自动模式只显示
等待玩家确认角色的公开进度，不显示任何角色。完整结算后玩家端和大屏均显示全部角色、
最终胜方、胜因和每人的有符号积分变化及结算后总分。

**FR-057** 阿瓦隆界面必须支持账户 `light`/`dark`、300px 起手机竖屏、桌面、鼠标、键盘、
触控、`focus-visible` 和减少动态效果。十名参与者、长中英文、角色编辑、历史记录和确认层
不得产生页面级横向溢出；主要操作不依赖 hover。

**FR-058** 阿瓦隆可使用现有账户音量控制的本地短提示音表示轮到本人、投票公开、任务结算
和终局，但声音不得成为唯一状态载体。音量 `0`、自动播放被阻止或音频 API 失败不得阻塞
命令；运行时不得引入公网字体、图标、规则、语音或其他远程资源。

## 6. 用户流程或调用流程

### 6.1 管理员默认设置

1. 可信 LAN 用户直接进入 `/admin`，展开阿瓦隆设置卡片。
2. 管理员选择默认自动/手动模式、默认奥伯伦规则、默认押分，并分别编辑 5–10 人唯一预设。
3. 界面按原版善恶人数、必选角色和重复角色规则即时提示；服务端重新校验全部平台与游戏设置。
4. 一个版本化幂等命令原子保存通用、扑克和阿瓦隆设置；失败时全部保持原值。
5. 保存结果初始化后续新房间，既有房间和活动对局不被暗改。

### 6.2 创建、加入与准备

1. 已登录用户在大厅选择“阿瓦隆”，创建房间并设置名称、模式、预设/自定义角色、
   奥伯伦规则和押分。
2. 房主加入为自动准备成员；其他账户加入后准备或取消，活动对局加入者先观战。
3. 实际在线准备人数达到 5–10 后，系统选择对应人数预设或验证自定义配置。
4. 若存在未准备成员，房主确认他们本局观战，再明确开始。
5. 服务端在同一事务中托管每人押分、冻结参与者和配置、随机角色及起始队长。

### 6.3 自动认角色

1. 每名参赛者看到默认遮盖的私密区并主动查看。
2. 私密区只显示本人角色和 FR-021 允许的关系；玩家可立即隐藏并随时重新查看。
3. 每人独立确认已查看；公共界面只显示确认进度。
4. 全员在线确认后进入第一项任务的队伍提名。

### 6.4 手动认角色

1. 每名参赛者只在私人设备查看本人角色并确认。
2. 房主端/公共大屏根据实际角色组合展示“天黑请闭眼”步骤。
3. 房主按顺序推进邪恶互认、梅林认人和派西维尔认人；玩家在线下按原版动作完成。
4. 第一次提名前可重新开始整套步骤；开始提名后不可通过网站补发自动知识。
5. 全员角色确认且房主完成夜间步骤后进入第一项任务。

### 6.5 组队、投票与任务

1. 当前队长讨论后选择规定人数并提交队伍。
2. 全部参赛者秘密投票；全员提交后同步公开个人票。
3. 否决则增加连续否决数并轮转队长；第五次否决立即邪恶胜。
4. 通过则入选成员秘密提交任务选择；善方只能成功，邪恶可成功或失败。
5. 全员提交后只公开成功/失败张数，按阈值记录任务结果。
6. 未终局则进入下一任务并轮转队长；三次失败邪恶胜，三次成功进入刺杀。

### 6.6 刺杀、结算与下一局

1. 三次成功后邪恶可讨论，只有刺客从不泄露阵营的候选列表中提交一次目标。
2. 命中梅林则邪恶胜，否则善方胜。
3. 服务端原子返还胜方自身押分、分配败方押分、保存结果并进入完整结算。
4. 玩家端和大屏公开全部角色、胜因、每人积分变化和结算后总分。
5. 房间保持在局间准备；成员可退出/加入、修改配置、重新准备，由房主开始下一局。

### 6.7 作废、断线与恢复

1. 需要某玩家操作而其断线时保持等待，房主可暂停、恢复或作废。
2. 活动参赛者退出、移除或删除会先原子作废本局并退回全部押分，再处理成员/账户。
3. 刷新和控制接管从服务器恢复同一角色、阶段和已提交秘密状态，本地未提交选择丢弃。
4. 服务重启恢复已确认对局和押分，清除连接/准备及本机遮盖显示状态；玩家重连后继续。

## 7. 数据、接口与状态

- 共享游戏类型必须至少支持 `texas-holdem` 和 `avalon`，以判别联合或等价严格类型分别承载
  Poker/Avalon 配置、状态、投影和结果；不得在一个大量可选字段对象中允许非法混合状态。
- `GlobalSettings.avalon` 至少保存默认模式、默认奥伯伦规则、默认押分和以玩家人数为键的
  六套角色预设。旧快照缺失时补 FR-010–FR-011 默认值并原子持久化。
- `AvalonRoomConfig` 至少表达认角色模式、角色来源、房间角色配置、奥伯伦规则、押分和
  房主转让时限；活动 `AvalonGameState` 保存不可变配置快照。
- 阿瓦隆状态至少区分：局间准备、角色确认、手动夜间、队伍提名、队伍投票、任务提交、
  刺杀、完整结算和作废。暂停属于房间控制状态，不得丢失内部阶段。
- 活动状态必须保存局号、冻结参与者/座位、角色映射、知识规则、起始/当前队长、当前任务、
  所需人数/失败阈值、队伍、秘密票、秘密任务选择、公开历史、连续否决数、任务轨迹、
  角色确认、夜间步骤、刺客目标、托管押分、版本和最终结果。
- 玩家投影必须由服务器根据账户、有效控制租约、是否冻结参赛者、模式、角色和阶段生成；
  display/观众只收到公共子集。完整原始状态不得直接序列化到 WebSocket。
- 阿瓦隆命令至少覆盖设置更新、准备、开始、角色确认、夜间推进/重启、队伍提交、投票、
  任务选择、刺杀、暂停/恢复、作废、退出/移除及系统恢复所需动作。每个写命令使用命令 ID、
  期望平台版本和期望游戏版本。
- 账户分数、赛季基础分、排行榜分数和历史分数使用有符号安全整数。游戏金额、押分、
  扑克筹码、下注、底池和流水单条金额继续使用非负安全整数，通过方向表达增减。
- 阿瓦隆结果必须成为游戏无关参赛事实的数据源；正常结果有效，作废结果无效。历史赛季
  删除必须清理相应阿瓦隆结果和流水；账户删除必须匿名化保留结果中的公开身份。
- 公开结果可保存全部终局角色，因为完整结算已公开；进行中角色映射仍属于私有恢复状态，
  不得进入大厅或管理摘要。
- 持久化继续复用 SQLite 事务、WAL、版本化 JSON 快照和 `processed_commands` 幂等结果。
  是否拆出新的 SQL 表留给后续设计，但不得改变可观察的原子性、恢复和卷兼容结果。

## 8. 异常、边界与恢复

- 角色数量、阵营数量、特殊角色重复、缺少梅林/刺客、5 人派西维尔搭配、准备人数、队伍
  人数、投票者、任务成员、善方失败牌、刺客身份或阶段不合法时，服务端必须无变化拒绝。
- 管理员预设在保存时按对应人数独立校验；一个人数无效使整个全局设置保存失败。房间使用
  旧快照时，管理员后续修正不得中途替换房间配置。
- 阿瓦隆押分小于 2、非整数、非安全整数或托管后任一有符号总量溢出时不得开始。账户余额
  为任意负数本身不是拒绝原因。
- 德州扑克余额检查移除后，买入/补码仍受正数、房间上下限、时点、版本和安全整数约束；
  不能把“允许负账户分数”误实现为允许负买入、突破最大买入或创造筹码。
- 排行榜、账户设置、管理员账户列表、结算和历史快照必须正确渲染负号和大安全整数，不得
  把负分截断为零、按字符串错误排序或发生窄屏不可读。
- 任何积分/押分/扑克转移失败必须回滚完整成组流水。检测到守恒差额、负游戏资产、孤立托管
  或安全整数溢出时服务端不得保存状态。
- 投票和任务选择在提交前只存在于本地草稿；权威状态更新使草稿过期时必须清空并提示。
  已提交选择不可撤销，但重复幂等请求只重放原结果。
- 全员提交前，响应长度、公开进度、动画顺序和错误信息不得泄露具体投票或任务选择。
  普通日志不得记录角色映射、知识名单、投票内容、任务内容或刺客未提交目标。
- 刺杀候选不得由服务器过滤成只有善方。刺客断线时无限等待；房主和其他邪恶不得代替提交。
- 活动玩家删除必须先作废并处理押分，再按既有管理员语义处理房主转让、账户正/负分退役、
  租约失效和匿名化；全部步骤必须在一个事务中全成或全败。
- 房主断线超时后可向在线成员转让房主，但断线参赛者仍保留角色和行动位并阻塞所需操作。
  无在线房主候选时安全作废、退款并关闭房间。
- 服务重启恢复已确认角色、投票、任务选择、公开历史、押分和阶段；连接和局间准备归一化
  为离线/未准备。活动局角色确认可保留为已确认事实，但本机角色显示必须重新遮盖。
- 作废状态不得公开角色；完整结算状态必须公开角色。恢复代码必须保留该边界，不能把所有
  终止状态统一投影。
- 旧客户端不要求长期兼容新服务命令，但服务端必须拒绝跨游戏或缺字段请求且不损坏数据。
  正式容器内 Web 与服务端同步发布。
- 运行或升级失败继续依赖现有 Docker 卷、健康检查、自动化备份与回退；不得删除固定卷、
  固定备份或未知恢复现场。本功能验收不等于正式服务器发布。

## 9. 非功能需求

**NFR-001 数据完整性**：有符号账户分数、阿瓦隆押分、扑克资产、发行和正/负退役必须以
安全整数保持守恒、可审计、无重复且全成或全败；游戏内部金额仍不得为负。

**NFR-002 隐私**：活动角色、自动知识、未公开票、任务选择和刺杀目标只进入规则允许的本人
有效租约投影；观众、大屏、管理员和日志不得越界。完整结算公开与作废不公开必须明确区分。

**NFR-003 服务端权威与并发**：角色分配、合法动作、阶段、队长、任务结果、胜负和积分均由
服务端决定；重复、过期、接管和并发命令只产生一个结果。

**NFR-004 恢复**：刷新、断网、控制接管和服务重启不得重分角色、改票、改任务、重复托管/
派分或提前公开秘密；未提交客户端草稿不成为权威状态。

**NFR-005 兼容**：现有账户、赛季、扑克房间/手牌、排行榜、设置、管理员、公共大屏、
SQLite 卷和部署接口可升级。有符号分数新语义不得破坏扑克正数筹码规则。

**NFR-006 响应式与可访问性**：桌面和 300px 起手机竖屏无页面级横向溢出；十名玩家、
任务历史、自定义角色和底部操作均可达；键盘、触控、鼠标、`focus-visible` 和减少动态
效果可用，信息不只依赖颜色、hover 或动画。

**NFR-007 本地化**：全部新角色、规则、按钮、步骤、状态、胜因、积分、确认和错误提供
简体中文与英文；候选、阵营和角色术语在两种语言中保持相同隐私含义。

**NFR-008 容量与性能**：保持约 15 个在线账户、1–2 个活动房间及对应多开大屏目标。
十名玩家投影、公开历史、角色编辑和防窥切换不得造成无界 DOM、持续整页重绘或跨房串流。

**NFR-009 离线运行**：运行时不得依赖公网、CDN、云数据库、第三方身份、远程规则、远程
字体或远程语音；全部代码、图标、文本和可选音效随构建本地提供。

**NFR-010 工程边界**：共享游戏判别、阿瓦隆纯状态机、平台领域、持久化、Fastify 和 React
必须保持严格 TypeScript、ESM 与 workspace 边界；不得把阿瓦隆规则复制到多个客户端分支。

**NFR-011 可观察性**：结构化日志可定位非法配置、阶段拒绝、并发、恢复、守恒和溢出，
但不得记录角色、知识、票、任务选择、刺杀目标、连接令牌或不必要完整请求体。

**NFR-012 发布安全**：生产构建必须无运行时公网引用并可由现有 x86-64 iStoreOS Docker
路径运行；正式部署、固定卷切换和真实服务器验收仍需独立授权。

## 10. 初步实现方向与影响范围

- 把共享房间、配置、投影和结果改为以 `gameType` 判别的严格联合，同时保留扑克现有字段和
调用者兼容；大厅和公共大屏按游戏类型渲染。
- 新增独立的纯 TypeScript 阿瓦隆规则包或等价隔离模块，集中维护人数表、角色校验、知识
投影、阶段转换、投票、任务、刺杀和终局，不把规则散落在 Fastify 或 React。
- 平台领域负责跨游戏房间成员、准备、房主、账户有符号积分、押分托管、结果参赛事实、
账户删除/匿名化和总量不变量；阿瓦隆规则引擎不直接修改 SQLite。
- Fastify 增加阿瓦隆命令校验、分发、角色化 WebSocket 投影和公共 display 分支，继续
复用命令 ID、期望版本、租约和 `PlatformStore.execute()` 事务。
- Web 在大厅增加游戏选择，在管理员增加阿瓦隆设置卡，在房间增加等待/自动认人/手动夜间/
  对局/刺杀/结算视图；复用现有固定容器、portal、主题、账户音量和错误处理原语。
- 扩展现有 SQLite JSON 恢复归一化，为旧设置补阿瓦隆默认值并接受有符号分数；不重写
  已冻结历史结果。负分写入后的旧镜像回退依赖整库备份。
- 重点测试范围包括阿瓦隆纯规则矩阵、角色知识隔离、投票/任务隐私、刺杀、五次否决、
  押分守恒、有符号溢出、扑克负账户分数兼容、账户删除、SQLite 恢复、WebSocket 角色投影、
  Chromium/WebKit 核心流程、300px、容量和生产静态资源。
- 预计影响 `packages/contracts`、`packages/domain`、`packages/persistence`、
  `apps/server`、`apps/web`、测试支持和相关测试；可能新增 `packages/avalon`。不要求修改
  部署状态机或 Docker 数据卷接口。
- 后续 `$plan-feature-implementation` 应默认以一个连贯阶段审计本功能，但可因共享房间
  判别、有符号资产迁移和秘密投影的组合风险选择 expanded 细节；本需求不预先拆分阶段。

## 11. 验收标准

| 验收 | 层级 | 可观察结果 |
| --- | --- | --- |
| AC-001 | core | 大厅可创建、发现、加入和返回阿瓦隆房间；扑克房间行为和字段保持正确，跨游戏命令无变化拒绝。 |

| AC-013 | core | 只有刺客可从不泄露阵营的候选列表提交一次目标；命中梅林邪恶胜，未命中善方胜，随后公开角色。 |
| AC-014 | core | 押分至少 2 且默认 100；余额任意正负均可开局托管。正常结算每名败方净扣押分、每名胜方正收益、余数顺序稳定且净变化总和为零。 |
| AC-015 | core | 账户、赛季基础分、排行榜和历史支持有符号安全整数；扑克买入/补码可使账户负分但仍遵守正数、时点和桌上限额，游戏资产不为负。 |
| AC-016 | core | 重复、过期、并发、持久化失败、守恒失败或安全整数溢出不产生部分托管、派分、流水、结果或阶段推进。 |
| AC-017 | core | 活动参赛者退出/移除/删除、房主作废或安全关闭会原子作废并退款，不进入有效参赛事实；作废不公开角色。 |
| AC-018 | core | 完整结算保持至下一局明确开始，显示全部角色、胜因、每人积分变化和总分；成员可变更配置并重新准备，角色重新随机。 |
| AC-019 | core | 观战成员和匿名大屏只得到公共状态，不占当前角色/投票/任务名额；加入、退出和多开不改变对局。 |
| AC-020 | core | 公共大屏同步参与者、队长、公开队伍/票、任务汇总、轨迹、否决和结算，无任何玩家操作或活动秘密。 |
| AC-021 | core | 玩家端按上方参与者、中间任务局势、下方操作区完成全流程；中英文、桌面、300px、键盘和触控无页面级横向溢出。 |
| AC-022 | core | 刷新、断网、控制接管和服务重启恢复相同角色、已提交票/任务、公开历史、押分和阶段，不重复分配或提前公开。 |
| AC-023 | core | 所需玩家断线时不自动行动；房主暂停/恢复/作废、房主超时转让和无候选安全关闭均不破坏隐私或资产。 |
| AC-024 | core | 正、零、负账户删除及活动阿瓦隆删除保持有符号守恒、租约失效、历史匿名化和同名隔离；失败时完整回滚。 |
| AC-025 | core | 既有扑克核心规则、私牌投影、账户偏好、管理员、赛季、历史、公共大屏和旧 SQLite 快照升级后继续正确。 |
| AC-026 | core | 正常阿瓦隆结果产生游戏无关参赛事实并使所有实际参赛者进入当前/未来排行榜；观众和作废局不计，历史删除清理关联结果。 |
| AC-027 | core | 与变更层匹配的 lint、严格类型、平台/服务、扑克、阿瓦隆、实时隐私、核心浏览器、容量、生产构建和静态资源硬门禁全部通过。 |
| AC-028 | supplemental | Chromium 与 WebKit 中角色遮盖、十人布局、自定义角色、夜间步骤、投票、任务、刺杀和结算不存在影响 core 操作的差异。 |
| AC-029 | supplemental | 约 15 个在线账户、1–2 个扑克/阿瓦隆房间及多开大屏下，秘密投影不串房，历史和界面节点保持有界且无明显持续卡顿。 |
| AC-030 | supplemental | 结构化日志可定位配置、阶段、并发、溢出、守恒和恢复拒绝，且不含角色、知识、票、任务选择或敏感令牌。 |
| AC-031 | supplemental | 独立界面审阅确认阿瓦隆与德州扑克产品风格一致，同时公共状态、私密状态、危险操作和当前行动具有清晰层级。 |
