# 平台易用性与数据管理增强：需求

- 功能 ID：`platform-usability-and-data-management`
- 工作流 schema：`3.2`
- 批准日期：`2026-07-29`
- 项目基线：`d55c2568abcb2b67871c58b53559d7b05a32232c`
- 基线产品需求：[../home-party-game-platform/effective-requirements.md](../home-party-game-platform/effective-requirements.md)（已应用至 `change-2`）
- 基线房间体验需求：[../poker-room-experience-upgrade/effective-requirements.md](../poker-room-experience-upgrade/effective-requirements.md)（已应用至 `change-0`）

## 1. 背景与目标

现有家庭局域网聚会游戏平台已经提供账户、房间、赛季、排行榜、德州扑克、公共大屏和 SQLite 恢复。实际聚会使用暴露出一组相互关联的易用性和数据维护问题：

1. 玩家在一手完整结算后、下一手开始前退出时，房间座位虽被移除，但旧手牌玩家记录仍可能参与投影和下一手筹码选择，导致其他玩家仍看到该玩家，退出者重新加入后也不能正常参赛。
2. 移动牌桌的玩家信息将剩余筹码与本轮下注压在同一行并可能截断；等待室和牌桌顶部在窄屏下拥挤、按钮堆叠或与房间及当前玩家名称重叠。
3. 现有静音入口占用顶部空间；自动同步时出现“权威状态已更新”等面向开发者的正常流程提示，容易使聚会玩家困惑。
4. 新赛季会立即把所有账户列入排行榜，未反映“实际玩过游戏”的语义；横向赛季标签随历史增长会持续占用空间。
5. 平台缺少清理误建账户和旧赛季的用户界面与服务端能力。

本功能的目标是修复两手之间的玩家退出生命周期，简化所有游戏房间的顶部控件和正常流程文案，改善移动端下注信息，按真实参赛记录显示排行榜，并在可信 LAN 模型下提供明确、原子且可恢复边界清晰的账户与赛季删除能力。账户、赛季、排行榜、设置、大厅导航与数据管理属于可供后续游戏复用的平台能力；德州扑克专属设计只覆盖当前牌桌、手牌参与者和牌局生命周期，不得把平台界面或平台数据模型归入扑克专属边界。

## 2. 范围

### 2.1 包含范围

- 德州扑克完整结算阶段到下一手开始前的退出、投影、重新加入、买入、准备和下一手选人。
- 当前 Web 客户端的登录页、大厅、等待室、玩家牌桌、带身份观战和匿名公共大屏顶部控件。
- 移动端玩家座位中的剩余筹码与本轮下注展示。
- 当前及未来赛季的排行榜参赛资格与赛季下拉选择。
- 设置界面的账户管理和赛季管理入口，包括逐个删除、批量删除、危险操作确认、成功/失败反馈。
- 账户删除后的当前资产处理、会话失效、用户名复用和历史身份匿名化。
- 历史赛季的永久删除以及关联排行榜、手牌结果和资产流水删除。
- 旧 SQLite JSON 状态的兼容加载、删除状态持久化、重启恢复、命令幂等和并发校验。
- 简体中文/英文、键盘、触控、300px 窄屏、公共大屏隐私和离线生产构建兼容。
- 供后续其他游戏复用的平台边界：账户、赛季、排行榜、设置、大厅导航和数据管理保持游戏无关；语言和亮/暗主题切换只出现在登录页和大厅，不出现在任何游戏的等待、进行中、结算、观战或公共大屏界面。

### 2.2 不包含范围

- 不重新设计静音入口、音量控制、设备级音效设置或账户级音频偏好；本次仅移除现有静音按钮和静音状态的生效。
- 不新增管理员、密码、角色权限、账户所有权证明或互联网身份；任何已登录账户均拥有本功能的数据管理权限。
- 不新增删除撤销、回收站、应用内数据库备份或恢复界面；历史赛季永久删除只能依赖运维侧数据库备份恢复。
- 不回写或重新计算已有历史赛季排行榜的“玩过游戏”资格；历史快照仅受账户匿名化或显式赛季删除影响。
- 不修改德州扑克规则、下注合法性、结算、撤销、边池、隐藏牌投影或房间人数上限。
- 不修改自动化部署脚本、Docker 数据卷、服务器配置或正式 iStoreOS 服务；本功能允许在用户已授权的 iStoreOS 上使用隔离临时资源测试候选版本，但真实发布或正式服务切换仍需独立授权。
- 不修改已冻结的 `home-party-game-platform`、`poker-room-experience-upgrade` 或 `deployment-automation` 历史记录。

## 3. 已确认的项目事实与约束

1. 项目是 TypeScript ESM 单仓库，React Web 通过 Fastify HTTP/WebSocket 调用服务端命令，`PlatformDomain` 和扑克引擎维护权威状态，`PlatformStore` 在 SQLite 事务中保存整个 `PlatformSnapshot` JSON。
2. 当前 `leaveRoom` 会移除 `Room.seats` 和准备记录，但只把匹配的旧 `PokerState.players` 玩家筹码置零；完整结算后的投影和下一手筹码选择仍可能读取该旧记录。
3. `startSelectedHand` 以旧 `PokerState.players` 优先于新 `Room.seats.tableChips` 计算下一手筹码，因此同一账户退出后重新买入可能继续得到旧的零筹码记录。
4. `Room.seats` 是带身份成员权威集合，`PokerState.players` 只应表示当前手参赛者；匿名 display 不占成员名额。
5. `HandResultSummary` 已保存 `seasonId`、`outcome`、`participantAccountIds` 和 `reversedAt`，可作为当前及未来赛季参赛资格的权威来源。
6. 当前排行榜遍历所有账户；历史赛季保存不可变的用户名、头像、分数和排名快照；赛季选择当前使用横向按钮标签。
7. 当前音效是浏览器在牌局阶段变化时生成的短提示音，`party-muted` 本地状态和顶部按钮决定是否播放。
8. 语言和主题偏好是设备本地状态；当前登录、大厅、等待室、玩家牌桌、带身份观战和匿名大屏都渲染 `DeviceControls`。
9. 当前全局设置、新赛季等平台命令只要求有效账户控制租约，没有管理员模型。用户明确接受任何已登录账户均可删除账户和赛季。
10. 当前赛季资产守恒由发行流水、账户分数、桌上筹码、下注和底池共同校验；账户删除不得通过简单移除资产对象破坏守恒或审计。
11. 项目只部署在可信家庭 LAN，但可信 LAN 不放宽服务端授权、幂等、并发、隐私、资产、持久化和恢复正确性。
12. 生产运行时不得新增公网、CDN、云数据库或第三方身份依赖；构建产物不得引用运行时公网资源。
13. 工作区在需求批准前保持干净，基线提交为 `d55c2568abcb2b67871c58b53559d7b05a32232c`。
14. 德州扑克只是当前大厅中的第一个游戏。平台账户、房间发现、赛季、排行榜、设置、数据管理和共享导航不得依赖扑克术语、扑克状态或扑克组件；当前扑克手牌结果可以作为首个参赛记录适配器，但后续游戏应能通过同一平台级参赛边界接入。

## 5. 功能需求

### FR-001 两手之间退出与重新加入

1. 当房间处于等待首局、完整结算 `complete` 或其他允许自行退出的非活动手牌状态时，退出成功必须在同一服务端事务中：
   - 从 `Room.seats`、等待/结算准备列表和后续手牌候选中移除账户；
   - 结清并兑换该账户权威剩余桌上筹码；
   - 清除该账户对旧 `PokerState.players` 的后续成员、筹码和投影影响，同时保留已完成手牌及结算历史；
   - 更新房间版本和平台版本并广播新投影。
2. 退出成功后，其他玩家、大厅、带身份观众和匿名大屏不得继续把该账户显示为当前房间成员或参赛者。
3. 退出账户回到大厅后必须能够以新的合法买入重新加入同一可加入房间；新买入、筹码、角色和准备资格不得被退出前的旧手牌记录覆盖。
4. 当前活动手牌中普通参赛者仍不得自行退出；房主退出、房主踢人和活动手观众退出继续遵守现有有效需求。

### FR-002 移除当前静音入口但继续播放音效

1. 玩家牌桌不得显示现有静音/开启音效按钮。
2. 现有 `party-muted` 等本地静音值不得继续阻止阶段提示音；已有设备即使曾选择静音，升级后也按当前阶段音效规则播放。
3. 牌局阶段变化时继续播放现有短提示音，用户本次版本无法在产品内静音。
4. 后续重新设计静音或音量入口属于新需求，不得在本次实现中扩展。

### FR-003 移动端本轮下注展示

1. 玩家、带身份观众和公共牌桌在移动尺寸展示每位可见玩家时，必须分别显示：
   - 剩余桌上筹码；
   - 本轮下注 `currentBet/roundBet`。
2. 两项信息必须具有中英文可理解标签，在窄屏座位卡中允许换行，不得因省略号、单行截断或顶部滚动而隐藏本轮下注数值。
3. 桌面布局可保持紧凑，但不得改变服务端数值、下注语义、玩家顺序或隐私投影。

### FR-004 顶部控件与跨游戏共享规则

1. 语言和亮/暗主题切换只允许出现在登录页和大厅。
2. 德州扑克等待室、玩家牌桌、结算层、带身份观战和匿名公共大屏必须移除右侧语言和主题控件。
3. 后续新增游戏必须复用同一规则：任何游戏的等待、进行中、暂停、结算、观战和公共展示界面都不得自行放置语言或主题切换；玩家应先回到大厅切换。
4. 移除右侧控件后，等待室和牌桌顶部应优先容纳返回大厅、离开房间、房主结束游戏、房间名称和当前玩家身份。
5. 在 300px 和常见手机竖屏下，三个左侧操作不得逐个形成难以使用的竖向按钮列，也不得与房间名称或当前玩家名称重叠；允许把操作组放在独立横向行或使用其他不重叠的响应式布局。
6. 登录页和大厅的语言、主题切换仍保持设备本地持久化、键盘/触控可用和不重载。

### FR-005 面向聚会玩家的状态与错误文案

1. 下注缓存因服务端状态、版本、行动者或合法额度变化而失效时必须安全清空，但正常同步不得显示“权威状态已更新”“版本变化”“服务器拒绝”等技术性提示。
2. 正常成功、等待、准备、结算和设置流程只显示朋友能够理解的简短业务文案；无必要时可以不显示提示。
3. 发生真实错误时必须显示友好、可行动的中英文说明，并允许同时显示稳定错误代码，格式应使错误代码明显属于诊断信息而不是正常状态。
4. 未识别错误不得只显示原始异常、堆栈或内部数据；可以显示通用友好说明和安全的错误代码。
5. 日志和界面均不得因错误提示泄漏隐藏牌、私钥、连接令牌或不必要的账户数据。

### FR-006 当前及未来赛季的参赛排行榜

1. 当前赛季排行榜只显示至少参加过一手符合下列全部条件的账户：
   - 手牌 `seasonId` 等于所选当前赛季；
   - 手牌已产生持久化结果；
   - `outcome` 不是 `void`；
   - 结果未被撤销；
   - 账户 ID 出现在 `participantAccountIds`。
2. 玩家是否获胜、是否主动行动、是否弃牌、净筹码变化是否为零都不影响参赛资格。
3. 仅创建账户、获得基础分、加入房间、买入、准备、观战或参加最终作废的手牌都不得使账户进入排行榜。
4. 新赛季开始时排行榜可以为空；首手合法结算后，全部实际参与该手的账户进入榜单并按现有分数排序和并列规则排名。
5. 当前赛季归档时，历史赛季快照只包含该赛季符合参赛资格的账户。
6. 本规则立即应用于升级时的当前赛季和所有未来赛季；已有历史赛季快照不因本规则重新筛选，但仍受账户匿名化和显式赛季删除影响。
7. 排行榜资格判断必须位于平台级参赛结果边界。当前版本从德州扑克 `HandResultSummary` 适配参赛事实；不得让大厅、排行榜或赛季归档直接依赖扑克牌型、底池、下注或牌桌组件，后续游戏应能提供等价参赛事实而不重写平台界面。

### FR-007 赛季下拉选择

1. 排行榜不得再以横向标签列出赛季，必须提供一个可访问的单一赛季下拉/listbox。
2. 选择项至少包含当前赛季和所有未删除历史赛季；默认选择当前赛季，历史赛季按开始或结束时间从新到旧排列。
3. 选中历史赛季后显示其已保存排行榜快照；选中当前赛季后显示 FR-006 的动态排行榜。
4. 当前选择的赛季被删除、数据刷新后不再存在或新赛季开始时，选择必须安全回退到最新当前赛季。
5. 赛季数量增长不得造成页面横向溢出；控件必须支持键盘、触控、Esc、焦点恢复和 300px 窄屏。

### FR-008 账户管理与删除

1. 设置界面必须提供独立“账户管理”入口，列出当前全部未删除账户并提供逐个删除和“删除全部”操作。
2. 任何持有有效账户控制租约的已登录用户都可以删除任意账户；不新增管理员权限。
3. 逐个删除允许选择当前登录账户本人：
   - 删除成功后当前会话和本地最近账户立即失效；
   - 客户端返回登录页；
   - 同一用户名后续可以创建新的独立账户。
4. “删除全部”必须跳过发起操作的当前账户，只删除其他账户；界面必须明确显示受保护账户和将删除的数量。
5. 删除其他账户成功后，该账户的所有控制租约失效；其在线客户端在下一次投影、命令或连接检查时必须退出到登录状态，不得继续控制平台。
6. 删除账户必须从当前账户列表、当前排行榜、当前赛季活动资产和可登录身份中移除目标，同时以明确的资产退役/注销记录维持当前赛季资产守恒和审计一致性。
7. 删除成功不得修改其他账户分数、已确认房间结果或当前赛季身份。

### FR-009 删除账户后的历史匿名化

1. 删除账户不得删除仍需保存的其他赛季、已完成手牌或资产审计记录；目标账户在所有保留历史中的用户名和头像必须被不可还原的中性占位身份替换。
2. 历史排行榜、手牌结算和其他用户可见投影不得暴露原用户名、原头像或可直接恢复身份的内部标识。
3. 同一历史记录中存在多个已删除玩家时，结构和结算含义必须仍可区分，不得因相同占位名称合并玩家、排名、筹码变化或获胜记录。
4. 匿名化后的历史不得因为同名账户重新创建、服务重启或重新进入大厅而恢复原身份或绑定到新账户。
5. 资产流水可以保留满足审计和守恒所需的内部非展示引用，但公共/普通账户接口不得将其解释为原账户身份。

### FR-010 赛季管理与删除

1. 设置界面必须提供独立“赛季管理”入口，列出当前赛季和全部未删除历史赛季，并提供逐个删除和“删除全部历史赛季”操作。
2. 最新的 `current` 赛季始终受保护：
   - 不得逐个删除；
   - 批量删除必须跳过；
   - 界面必须明确标识其受保护状态。
3. 逐个删除历史赛季成功后，必须永久删除该赛季：
   - `Season` 历史记录；
   - 历史排行榜快照；
   - 该 `seasonId` 的手牌结果；
   - 该 `seasonId` 的资产流水和只属于该赛季的匿名化记录。
4. “删除全部历史赛季”必须在一个事务中删除全部历史赛季及上述关联数据，只保留当前赛季。
5. 删除历史赛季不得改变当前赛季 ID、基础分、账户资产、当前排行榜、账户身份或其他保留赛季。
6. 平台不提供应用内撤销或回收站；确认文案必须说明永久性。恢复只能依赖运维侧 SQLite 备份。
7. 删除后，赛季下拉和所有大厅订阅必须立即移除目标；重启后不得重新出现。

### FR-011 删除安全、并发与错误处理

1. 任意账户或赛季删除只有在不存在任何未关闭房间时才允许执行；存在 waiting、in_progress、paused 或其他受管房间时，服务端必须完整拒绝并返回友好错误及错误代码。
2. 逐个删除和批量删除都必须在提交前显示目标或数量、保护项、历史匿名化/永久删除影响和不可撤销说明，并要求明确确认。
3. UI 隐藏、禁用或确认框不得替代服务端权限、房间、目标、当前赛季、当前账户、版本和租约校验。
4. 每个删除命令必须使用现有命令 ID、期望平台版本、有效控制租约和 SQLite 事务；成功要么完整提交，要么无变化失败。
5. 重复命令只能重放同一结果；过期、并发、目标已删除、目标变为受保护对象或持久化失败不得导致部分删除、重复资产退役、孤立赛季引用或错误删除新对象。
6. 批量删除是单一原子操作，不得因为其中一个目标失败而留下部分批次。
7. 删除请求无可删目标时应安全成功或返回明确无操作结果，不得删除保护项。

### FR-012 持久化、恢复与兼容

1. 删除账户、历史匿名化、资产退役、删除赛季和排行榜资格必须随 `PlatformSnapshot` 原子持久化并在 SQLite/WAL 重启后保持。
2. 旧数据库缺少本功能新增字段或匿名化/退役结构时必须兼容加载并补安全默认值；不得重写已有历史身份，除非对应账户在本功能中被明确删除。
3. 升级、重启或连接恢复不得使已删除账户、已删除赛季、被匿名化身份或已清理的两手间成员重新出现。
4. 保留的活动手牌、隐藏牌、房间成员、资产、准备恢复规则、公共大屏和既有历史快照必须保持现有兼容语义。
5. 新增删除命令应保持现有 HTTP/WebSocket 命令信封兼容；旧客户端不调用新命令时可继续使用既有平台行为。

### FR-013 双语、无障碍与共享产品规则

1. 所有新增入口、标签、占位身份、确认、空状态、成功和错误文案必须提供简体中文与英文。
2. 账户/赛季管理、赛季下拉、确认框和移动座位信息必须支持键盘、触控、`focus-visible`、可读名称和合理焦点恢复；危险操作不得只靠颜色表达。
3. 设置内容继续遵守固定外框、标题/操作可达、内容内部滚动和 300px 无页面级横向溢出。
4. 共享语言/主题控件规则必须位于可供后续游戏复用的产品/组件边界，而不是仅对德州扑克选择器做一次性 CSS 隐藏。
5. 新文案不得使用“权威状态”“聚合版本”“租约”等面向开发者的正常流程术语；错误代码只在错误状态中显示。

## 6. 用户流程或调用流程

### 6.1 两手之间退出并重新加入

1. 当前手完整结算，房间进入 `complete`。
2. 玩家点击顶部“离开房间”，阅读确认并提交。
3. 服务端按最新版本结清筹码、移除座位/准备/旧玩家后续影响并持久化。
4. 所有订阅者立即收到不含该玩家的房间或大厅投影；退出者回到大厅。
5. 退出者再次选择同一房间、输入合法买入并加入。
6. 新座位使用新买入且处于可准备成员状态；房主下一手选择时不读取退出前零筹码记录。

### 6.2 当前赛季排行榜

1. 新赛季开始后排行榜显示友好空状态。
2. 玩家仅创建账户、加入或观战时仍不出现。
3. 一手正常结算后，结果中的全部实际参与者进入当前榜单。
4. 用户从单个赛季下拉选择当前或历史赛季；若选项被删除则回退当前赛季。

### 6.3 删除单个账户

1. 已登录用户从大厅设置进入账户管理。
2. 用户选择目标，确认历史匿名化、会话/资产影响和不可撤销性。
3. 服务端确认无开放房间、租约和版本有效后原子删除账户、处理当前资产并匿名化保留历史。
4. 删除他人时，发起者留在设置或收到刷新后的列表；目标会话失效。
5. 删除自己时，当前会话和最近账户缓存清除，客户端返回登录页。

### 6.4 删除全部其他账户

1. 用户选择“删除全部”，界面显示将删除数量并说明当前账户受保护。
2. 用户明确确认后，服务端在一个事务内删除除发起者外全部账户、处理资产并匿名化历史。
3. 任一校验或持久化失败时全部回滚。

### 6.5 删除历史赛季

1. 用户从设置进入赛季管理；当前赛季显示为受保护。
2. 用户逐个选择历史赛季或选择删除全部历史赛季。
3. 确认说明永久删除排行榜、手牌和流水且应用内不可恢复。
4. 服务端在无开放房间、版本和租约有效时原子删除；大厅和下拉立即刷新。

## 7. 数据、接口与状态

1. `Room.seats` 继续作为当前房间带身份成员集合；`PokerState.players` 继续作为当前手参与者集合。完整结算退出必须使旧 `PokerState.players` 不再覆盖已离开或重新加入座位的当前成员状态。
2. `HandResultSummary` 的 `seasonId`、`outcome`、`participantAccountIds` 和 `reversedAt` 是当前德州扑克实现提供给平台级参赛结果边界的权威来源；不得以分数是否变化、流水金额或客户端访问记录推断“玩过”。平台排行榜和赛季归档只消费游戏无关的参赛事实，不读取扑克牌型、底池或下注状态。
3. 账户删除需要一种持久化、不可投影为原身份的退役/匿名引用，以同时满足：
   - 当前账户和资产删除；
   - 历史身份匿名化；
   - 当前赛季资产守恒；
   - 保留历史手牌和审计记录的结构完整。
4. 匿名历史必须使用中性中英文展示，不依赖已删除 `Account` 读取用户名或头像。
5. 删除历史赛季必须同时清理 `seasons`、`historicalSeasons`、匹配 `seasonId` 的 `handResults`、`ledger` 和仅属于该赛季的辅助记录。
6. 新增命令至少应覆盖单账户删除、批量账户删除、单历史赛季删除和批量历史赛季删除；具体命令名称由规划确定，但必须使用现有命令信封和服务端 Zod 校验。
7. 大厅投影必须提供设置管理列表和排行榜下拉所需的最小公开数据；不得把内部匿名化映射、流水引用或连接租约暴露给普通客户端。
8. 删除成功必须增加平台版本并触发大厅/房间订阅刷新；目标账户租约失效。
9. 本功能不要求独立 SQL 关系表；若规划选择扩展 JSON 状态，必须提供旧快照规范化和幂等恢复。

## 8. 异常、边界与恢复

1. 房间存在时，所有账户/赛季删除无变化失败，即使目标账户不在房间或目标赛季是历史赛季。
2. 当前赛季删除请求必须服务端拒绝；批量历史赛季删除不得包含当前赛季。
3. 批量账户删除不得包含发起者；逐个自删允许并在成功后终止会话。
4. 删除已删除目标、重复提交或 WebSocket 同步与删除竞争时，幂等结果和版本检查不得命中新创建的同名账户或新赛季。
5. 匿名化过程中任一历史记录、资产处理或持久化失败必须回滚账户删除；不得留下部分原身份和部分匿名身份。
6. 赛季删除过程中任一关联集合清理失败必须回滚整个命令；不得留下可选择但无快照的赛季或引用不存在赛季的用户可见结果。
7. 账户删除后同名重新创建产生新的账户、资产发行和会话，不继承旧分数、房间、准备、排名资格、手牌或匿名历史。
8. 当前赛季没有合格玩家、没有历史赛季、只有当前账户或只有当前赛季时，设置和排行榜必须显示友好空状态；批量操作不得误删保护项。
9. 自动提示音因浏览器自动播放政策不可用时不得阻塞牌局；本次不新增绕过浏览器策略的行为。
10. 错误界面可显示错误代码，但不得把成功代码、内部版本或正常同步事件当作用户提示。
11. 服务重启后连接与准备仍按现有安全规则重建；删除和匿名化是持久业务状态，不得回滚。
12. 运维备份恢复会按整个 SQLite 快照恢复到备份时状态；应用本身不提供细粒度删除撤销。

## 10. 初步实现方向与影响范围

### 10.1 初步方向

1. 在领域层建立明确的“完整结算后移除成员”路径，使退出同时协调座位、旧手牌玩家、准备、筹码、资产和投影；服务分发继续负责租约、版本、广播和房主特殊语义。
2. 在平台层建立游戏无关的参赛事实读取边界，当前由既有 `handResults` 适配合格账户且不依赖分数差；归档新赛季时保存已经过滤和重新排名的快照，未来游戏可接入同一边界而不修改大厅或排行榜组件。
3. 扩展平台持久状态和共享契约以表达已删除账户的非展示审计引用或等价结构；账户删除原子处理资产、租约、当前集合和历史匿名化。
4. 为历史赛季删除增加领域命令和关联数据清理；所有逐个/批量动作通过现有 `PlatformStore.execute` 事务和幂等命令结果。
5. Web 设置新增两个独立管理入口与确认 modal；排行榜用现有可访问选择控件模式替换标签。
6. 抽取或约束共享页面层级，使 `DeviceControls` 只在登录和大厅渲染；移动顶部和座位信息通过响应式布局而非技术文案或隐藏关键数值解决拥挤。
7. 删除现有静音状态分支和按钮，但保留阶段提示音调用；正常缓存失效改为静默，错误统一由友好说明加可选错误代码呈现。

### 10.2 预计影响区域

- `packages/contracts`：平台级参赛事实、删除/匿名化状态、管理投影和命令类型；扑克结果只作为当前游戏适配来源。
- `packages/domain`：平台级排行榜资格、账户删除、历史匿名化、资产退役、赛季删除、不变量和旧状态规范化；德州扑克完整结算退出协调保持在游戏生命周期适配边界。
- `packages/persistence`：继续使用事务与命令幂等；必要时补 JSON 状态迁移/恢复。
- `apps/server`：命令校验、分发、租约失效、错误代码和 WebSocket 广播。
- `apps/web`：设置管理、赛季选择、顶部控件、移动座位、静音按钮、提示文案和会话清理。
- `tests/platform.test.ts`、`tests/server.test.ts`、`tests/realtime.test.ts`、`tests/e2e/core.spec.ts` 及必要的容量/构建验证。
- 本功能不预计修改 Dockerfile、部署脚本、固定卷或生产环境配置。

### 10.3 跨阶段不变量

1. 任何中间阶段不得把删除仅实现为客户端隐藏；服务端始终拥有最终授权和持久化。
2. 在新增删除 UI 对用户可达之前，服务端的保护项、房间门禁、原子性、匿名化和资产守恒必须同时可用。
3. 在排行榜改用参赛资格后，当前赛季归档必须使用同一资格规则，避免当前榜与新历史快照不一致。
4. 在退出修复的任何中间状态，现有活动手退出、房主转让、踢人、隐藏牌和结算语义不得退化。
5. 语言/主题控件移除不得删除设备偏好或使登录/大厅不可切换。
6. 所有阶段必须保持旧数据可加载、项目可构建、公共大屏只读且隐藏牌隔离。
7. 账户、赛季、排行榜、设置、数据管理和大厅导航不得新增对德州扑克牌型、底池、下注或牌桌组件的依赖；扑克专属改动不得反向拥有平台页面。

### 10.4 主要风险

- 删除账户会同时影响当前资产、发行守恒、租约、历史快照和用户名复用，必须避免把物理对象删除等同于删除审计事实。
- 历史匿名化和历史赛季永久删除是不同语义：前者保留非识别记录，后者按用户确认清除整个赛季数据。
- 当前有效需求把旧手牌玩家用于完整结算和下一手筹码快照，退出修复必须保留已完成结果但停止旧记录覆盖新成员。
- 任何登录用户均可进行不可撤销管理是用户明确接受的可信 LAN 风险；确认和保护项不能被客户端绕过。
